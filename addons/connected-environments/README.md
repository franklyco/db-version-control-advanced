# Connected Environments add-on (connector)

Off by default. Enable under DBVC → Configure → Add-ons → Connected Environments, or `DBVC_Connected_Environments_Addon::save_settings(['dbvc_addon_connected_environments_enabled' => '1'])`. Kill switch: `define('DBVC_CONNECTED_EMERGENCY_DISABLE', true)`.

What it does: records save-side dirty markers for `bricks_global_classes`, `bricks_global_variables` and `service` posts (`wp.service`, identity = DBVC `vf_object_uid`; add `service` to DBVC's post types), snapshots each class/variable and the collection order in a leased background worker, keeps immutable `agency-control.observation.v0.2` events in a local outbox, and — once enrolled with a hub — delivers them outbound-only with per-event settlement and polls its hub inbox (store-before-ack). Received observations are stored for comparison and never applied to content.

Inspect: `wp dbvc connected status|jobs|objects|outbox|inventory`. Drive: `wp dbvc connected reconcile|process|deliver|resume` (or let WP-Cron run `dbvc_connected_process_observations` / `dbvc_connected_deliver_outbox`). Enroll: `wp dbvc connected enroll --hub=<url> --token=<invitation>`.

Implementation truth and verification: `docs/implementation/active/connected-environments-agency-control.md`. Design baseline: `docs/dropins/dbvc-connected-agency/`.

`wp.service` coverage: besides one projection per service post, the connector reports an inventory projection (`collection.order` under `wp-service-inventory-v1`, the sorted set of portable UIDs, complete only when every observed post has a `vf_object_uid`) on reconciliation and after each per-object change, so the hub can tell "never existed on the target" from "not observed yet". The Add-ons tab shows the received-observations inbox read-only.

Releases (M4 step 1): on its outbound poll the connector answers the hub's release payload requests with the canonical bodies it already recorded (only while the stored hash still equals the manifest hash; otherwise it reports a mismatch) and runs prepare requests as dry runs: identity by portable UID only (sidecar UID or `vf_object_uid`, plus hub-declared lineage links), current persisted state through the read-only observers, an exact whole-object patch or an explicit blocker per object, stored in `dbvc_ce_preparations` before it is reported. `wp dbvc connected release` runs this once; `preparations [--operation]` lists the receipts. Nothing is written to content.

Dependency ledger: each `ready` candidate on a receipt lists what its after-state references and whether this site has it (Bricks category and `var(--name)` references; service parent, terms and media) as present/selected/unresolved/unsupported; unresolved or unsupported entries block the item. Deletions prepare as `remove_object` (present) or no-op.

Apply (M5 step 1): a separate gate, "Allow approved releases to be applied here" (`dbvc_addon_connected_environments_apply_enabled`, off by default). While on, `wp dbvc connected release` also executes releases the hub approved for this environment: Bricks global classes/variables only, a fresh raw re-read of the option container, one conditional SQL write guarded by the receipt's storage fingerprint (a container edited in the meantime makes the operation `stale`, never an overwrite), a journalled before image, verification through the read-only observer and conditional compensation; the change is reported with `origin=apply`. `wp dbvc connected operations` lists the journal. Bricks CSS is not regenerated by apply.
