# Agency Control add-on (studio hub)

Off by default and independent of the connector. Enabling it installs the hub stores and registers `dbvc-agency/v1` routes for enrollment exchange, observation receipt and capabilities. Neither Bricks, the Visual Editor nor the connector is required on the hub. Kill switch: `define('DBVC_AGENCY_EMERGENCY_DISABLE', true)`.

Enrollment: `wp dbvc agency invite --client=<id> [--label=…] [--environment=<id>]` prints a single-use token once; the client runs `wp dbvc connected enroll --hub=<url> --token=<token>`. Each environment gets its own capability-less service user and WordPress application password; revoke with `wp dbvc agency revoke --environment=<id>`, clear a review hold with `release`.

Subscriptions: `wp dbvc agency subscribe --source=<env> --target=<env> [--domains=…]` (same agency/client only) and `subscribe-framework --environment --domain --instance --definition`; accepted events are routed into per-target deliveries served by `GET /inbox` + `POST /inbox/ack`, and into framework review items (state `observed`, awaiting M3 comparison). Comparison: `wp dbvc agency compare --source=<env> --target=<env>` classifies each object (hash level) against the pair's baselines; `baseline-confirm` records agreement explicitly (`--accept-absent` for one-sided absence); `link-instance` pairs independently enrolled lineages. Inspect: `wp dbvc agency status|environments|events|projections|subscriptions|deliveries|reviews|baselines|links|definitions|overrides`. See `docs/implementation/active/connected-environments-agency-control.md`.

Framework definitions: `wp dbvc agency definition-publish --definition=<uid> --version=<label> (--hash=<sha256> --domain --profile | --from-environment=<env> --from-instance=<uid> --domain --profile | --from-version=<label>) [--channel] [--order=<n>] [--desired]` records an immutable version (order is the studio's explicit `--order` or the publish sequence, never a comparison of labels); `definition-desire` marks a channel's desired version and flags that channel's approved overrides `needs_rebase_review`. `subscribe-framework … [--adopted-version] [--channel]` and `adopt-version --id=<subscription> --version=<label>` declare which version an instance follows. `override-approve --environment --domain --instance --definition --rationale=… [--hash]` records an exact approved hash with the frozen policy revision; `override-detach` ends it. `framework-status [--environment] [--definition] [--drift]` reports `drift` (`clean|local_drift|approved_override|override_changed|unknown`) and `version` (`current|behind_version|ahead_version|channel_mismatch|unknown`) per enabled framework subscription; it applies nothing and promotes no client edit.

Review items: every accepted observation of a framework-subscribed instance creates a raw review item; `wp dbvc agency review-classify [--environment] [--definition]` stamps open items with the drift/version state from `framework-status` and resolves those that are superseded, clean/current or approved-and-current; `review-resolve --id --note` closes one explicitly; `reviews [--state] [--environment] [--definition]` lists them.

Administrator panel: DBVC → Configure → Add-ons → Connected Environments shows environments, an invitation form (the token appears once in a notice after the redirect), open invitations, the framework status report and open review items. The panel is read-only apart from creating invitations; nothing there applies content.

Releases and preparation (M4 step 1): `wp dbvc agency release-create --source=<env> --items=domain:uid,…` fixes an immutable manifest from the source's current projections; the source's connector answers the hub's payload request on its next poll (`wp dbvc connected release`), the hub verifies each canonical body by hash and seals the release with a digest. `prepare-request --release=<uid> --target=<env>` asks a target to dry-run the release; its connector returns a receipt (exact whole-object patch with container fingerprint, or an explicit blocker per object) that the hub stores immutably with its digest and annotates with its own projections/baselines — `preparations --operation=<id>` shows it. A receipt expires and is never permission to write; nothing here applies content.

Deletions: `release-create --delete=domain:uid` releases a verified absence (the hub must hold the source's tombstone); targets prepare it as `remove_object` or no-op. The panel lists releases and prepare receipts.

Approval and execution (M5 step 1): `wp dbvc agency approve --operation=<prepare id>` binds a received ready/no-op receipt (release digest, receipt digest, target epoch, policy revision; expires with the receipt) for execution; the target's connector executes it on its next poll only while its apply gate is on and posts one execution receipt (`approvals --approval=<uid>` shows it); verified applied objects advance the pair baseline. `revoke-approval` withdraws an unconsumed approval.
