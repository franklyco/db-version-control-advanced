# R5.later-perf-b — persistent cache for Bricks' ACF field schema (option C)

**Status:** LANDED 2026-09-17 (E-161, D-083) — design confirmed by the maintainer on all four open questions (WS Form trigger via the theme, TTL 12 h, theme + plugin registrar scan, Bricks-level seed now / ACF-store warm-up deferred as perf-c). Default **off**; the maintainer enables it in Settings → Visual Editor. Parent: R5.later-perf (E-159, E-160).

## 1. What is left to remove

After perf-a, every frontend / REST request still spends ≈ 2.0 s in `Provider_Acf::get_fields()`: ACF materialising the whole schema (49 groups → 3 561 `acf_get_field()` loads through `acf/load_field`, with `acf_field__group::load_field` recursing into sub-fields). Warm it is 126 ms; ACF has no cross-request cache for PHP-registered fields. Bricks already caches the result of `get_fields()` in `wp_cache` (group `bricks`, key `md5('acf_fields' . wp_cache_get_last_changed('bricks_acf-field-group'))`, JSON-round-tripped so it is plain arrays, 1 day) — which only persists on hosts with an object cache. **This site has none, so the 2 s repeats on every request; and `get_fields()` is called by the ACF provider *and* the WP provider (`provider-wp.php:436`) — any fix must serve both.**

Measured on the live schema: the array is 501 top-level fields, **4.46 MB serialized, 0.33 MB gzipped**; `gzuncompress + unserialize` = **41 ms**; an options-table row read is ≈ 1–5 ms.

## 2. Strategy chosen: seed Bricks' own cache from a persistent DBVC transient

Rather than override any Bricks method, **pre-populate the exact `wp_cache` entry Bricks reads** before it registers providers (`init` 10000):

```
init@9999 (only when ! is_admin() || bricks ajax || bricks rest — Bricks' own condition)
  ├─ cached = get_transient('dbvc_ve_bricks_acf_fields:' . <cache_key_salt>)   ≈ 5 ms
  ├─ if cached && cached.fingerprint === current_fingerprint():
  │      wp_cache_set(md5('acf_fields' . last_changed), cached.fields, 'bricks', DAY)   → Bricks' get_fields() is a cache hit
  └─ else: miss → do nothing now; Bricks builds normally (2 s)
init@10003 (after Bricks' tag_registered@10002)
  └─ on a miss: fields = wp_cache_get(that key, 'bricks'); set_transient(gz+base64(fields) + fingerprint + built_at, TTL)
```

Why this is the best-value shape:

| Considered | Verdict |
|---|---|
| **Seed Bricks' `wp_cache` (chosen)** | Zero change to Bricks' code path; serves every caller of `get_fields()`; equivalence question reduces to "is the stored array what Bricks would compute now?"; independent of perf-a (works with stock Bricks, better with it). |
| Cache the finished tag registry (2 700 tags) | Tags embed whole field subtrees repeatedly → several × larger than the fields array; and `register_tag` is already 52 ms after perf-a. No. |
| Warm ACF's own field store (`acf_get_store('fields')`) from a cache | Would speed *every* ACF consumer (VE resolvers, `get_field_object`, forms), but skips `acf/load_field` for all of them on that request — much wider blast radius, and admin screens must never see it. Recorded as a possible perf-c, not now. |
| Compiled PHP cache file (`var_export` + opcache) | ≈ 8 ms instead of 45 ms per request, but executes generated code, needs a writable dir, per-server files. Not worth it for 35 ms. Revisit only if measurements say the 45 ms matters. |
| Storage: raw serialize vs gzip+base64 | 4.46 MB vs 0.44 MB per read; decode 32 vs 41 ms. **gzip+base64** — remote/managed DB hosts pay for bytes, and it survives text-column charset handling. |

Per-request budget with perf-a + perf-b on this site: transient read 5 ms + decode 41 ms + `register_tag` 52 ms ≈ **100 ms** where there is ≈ 3 500 ms today. Expected `/wp-json/` TTFB ≈ 4.1 s → ≈ 0.6–0.8 s (the rest is plugin/theme includes and Bricks `init_elements`).

**Prototype measurement (2026-09-17, read-only, seed from a scratch file, no site writes):** seeding Bricks' `wp_cache` at `init@9999` from the gzipped payload costs **46–47 ms**; the ACF provider's tags, its loop tags and the WP provider's tags are identical to a fresh build. `init` listeners: stock **4 204 ms** → seed only **2 037–2 062 ms** → seed + perf-a shim **566–617 ms**.

## 3. Always up to date: the invalidation design

The cached array is the *output* of ACF's load pipeline — including third-party `acf/load_field` filters — so freshness has to be enforced from several directions at once. Three layers:

### 3a. Fingerprint (computed on every request, must stay < 10 ms)

The transient is used only if its stored fingerprint equals the current one. Inputs:

| Signal | Cost | Catches |
|---|---|---|
| `acf_get_field_groups()` → per group `key`, `modified`, `local`, `active`, `menu_order`, `location`, `title` + count | ≈ 3–7 ms | admin-edited groups; groups added/removed/relocated in PHP or JSON |
| ACF version, Bricks version, DBVC version, PHP major | 0 | software updates |
| Active theme stylesheet + template + both versions; `filemtime` of both `functions.php` / `style.css` | < 1 ms | theme deploys |
| Newest `filemtime` under the active theme's `acf-json/` (if present) | ≈ 1 ms | JSON field edits |
| `filemtime` of every PHP file that registers local field groups — discovered once at build time (scan for `acf_add_local_field_group`), list stored with the cache, only `stat`ed per request | < 1 ms | PHP field edits without a version bump |
| Locale / current language (`get_locale()`, Polylang/WPML current language when present) — **part of the cache key**, not just the fingerprint | 0 | translated labels/choices differ per language |
| Event salt (§3b) | 0 (autoloaded option) | everything below |
| `dbvc_visual_editor_bricks_acf_fields_cache_salt` filter | site-defined | anything the site owner knows feeds its `acf/load_field` filters |

### 3b. Event salt (bumped by triggers → next request misses, rebuilds)

Stored as a tiny autoloaded option; bumped (and a warm-up scheduled, §3d) on:

- ACF: `acf/update_field_group`, `acf/delete_field_group`, `acf/trash_field_group`, `acf/untrash_field_group`, `acf/import_field_group`, `save_post_acf-field-group` (Bricks' own flush trigger), `acf/save_post` for `acf-field` posts (sub-field edits), `acf/options_page/save`? — no (values, not schema).
- Lifecycle: `switch_theme`, `activated_plugin`, `deactivated_plugin`, `upgrader_process_complete`, `wp_upgrade` (core), `updated_option` for `active_plugins`.
- Extensible: `save_post_{type}` for a filterable list of post types known to feed choices (`dbvc_visual_editor_bricks_acf_fields_cache_trigger_post_types`, default: `acf-field-group`, `acf-field`; the maintainer can add e.g. `wsf_form` since Vertical's `vf_populate_wsform_choices` reads WS Form forms), and a `do_action('dbvc_visual_editor_bricks_acf_fields_cache_flush')` any code can fire.
- Manual: **Rebuild now** button on the settings page; `wp eval '…AcfFieldsCache::flush();'`.

### 3c. Time and self-check

- **TTL** default 12 h (filterable): bounded staleness for anything the signals miss.
- **Daily verification cron** (`dbvc_ve_bricks_acf_fields_cache_verify`): builds fresh, compares `===` with the cached array; if they differ → replace the cache, bump the salt, and record `last_divergence` (time + a short diff summary: which field keys changed). The settings page surfaces it: divergences are the signal that some `acf/load_field` filter is dynamic and needs a trigger added.
- **Enable-time verification** (settings save): fresh vs cached must be identical or the switch is left on but inert (`state: verification_failed`), exactly like perf-a.

### 3d. Warm-up (editors should not pay the 2 s after an invalidation)

- On every salt bump, `wp_schedule_single_event(time(), 'dbvc_ve_bricks_acf_fields_cache_warm')` — the cron request is a frontend-context request, so Bricks builds and the miss path stores; the next editor request is a hit.
- In the admin request that caused the bump, additionally try a synchronous warm at `shutdown` **after** `fastcgi_finish_request()` when available (response already sent; invisible to the editor). Skipped when not available.
- Cold misses on ordinary requests still self-heal (build + store), so nothing depends on cron working.

## 4. Safety (same posture as perf-a — fail closed, no runtime writes on hits)

- Inert unless the switch is on (option `dbvc_visual_editor_bricks_acf_fields_cache_enabled`, filterable), Bricks' `Provider_Acf` is present and its `get_fields()` / `get_fields_locations()` / `required_hooks()` sources hash to a pinned fingerprint (the cache-key derivation and the JSON round-trip are what we rely on — a change there disables the seed), and the fingerprint has passed verification on this site.
- A hit only ever calls `wp_cache_set` on Bricks' key — the same call Bricks makes itself. A miss writes one transient after Bricks has finished; failures to read/decode/write are swallowed and leave Bricks' normal path in place.
- User-agnostic by design: the cache is keyed by locale, not user. If any `acf/load_field` filter tailors fields per user, the enable-time verification (run as the admin) vs the cron verification (run as no user) will disagree and the divergence is reported. Documented assumption.
- Admin requests never seed (Bricks registers no providers there) and never build — admin screens always see live ACF.
- Kill switch = untick; the transient is left in place (inert) and expires by TTL.
- Multisite: transients and options are per site.
- Size guard: if the encoded payload exceeds a cap (default 8 MB base64), do not store; report `payload_too_large` in status.

## 5. Surface

- Settings → Visual Editor → the existing "Performance — Bricks compatibility (site-wide)" group gains a second switch **Cache the Bricks ACF field schema** + status line (built at, size, fingerprint short hash, last verification result/time, last divergence, TTL) + **Rebuild now** / **Flush** buttons (nonce-protected admin-post actions).
- Class `Dbvc\VisualEditor\Performance\Bricks\AcfFieldsCache` (read/seed/store/flush/fingerprint/verify/status) + `AcfFieldsCacheTriggers` (hook registrations) + a small `AcfFieldsCacheCron`. Registered from `AcfTagIndexShim::register()`'s neighbour in `bootstrap()`; both switches are independent.
- Options: `…_fields_cache_enabled` ('0'), `…_fields_cache_salt` (autoloaded, tiny), `…_fields_cache_verified` (fingerprint or `failed:`), `…_fields_cache_meta` (last build/verify/divergence summary — not the payload). Transient: `dbvc_ve_bricks_acf_fields_<locale>` (payload). SETTINGS_VERSION 8 → 9.
- WP-Cron events: warm (single), verify (daily). Both registered only while the switch is on; unscheduled on disable.

- Differences from the plan, all in the "more up to date" direction: the JSON signal uses ACF's own `acf_get_local_json_files()` (47 files, 3 ms) so nested `acf/json/load_paths` directories count; the registrar scan also records every file that hooks `acf/load_field*` (theme filter files such as Vertical's `acf.php`, `acf-fields-autopopulate.php`, GardenAI) — 22 files on this site, ≈ 1.1–1.4 s once per build, 22 `stat`s per request; WS Form keeps forms in its own tables, so instead of a `wsf_form` post-type trigger the Vertical theme now bridges `wsf_form_{create,publish,trash,restore,delete}` → `do_action('dbvc_visual_editor_bricks_acf_fields_cache_flush')` (both checkouts, next to `vf_populate_wsform_choices`); one salt bump per request even when several triggers fire on one save.

## 10. Evidence (LocalWP, Bricks 2.3.8, ACF 6.6.2, PHP 8.4)

- Read-only: fingerprint 4–6 ms per request; registrar scan 22 files / 1.1–1.4 s at build; `verify(false)` with no payload → `stored_fresh` without writing; options untouched after every probe.
- In-process exercise of the real code path with the switch and verified marker forced by filters and the payload diverted to a scratch file: **miss → `capture` stored** (state `stored`, 451 KB) → **hit** (`seed` state `hit`, gate `ok`): `init` **4 996 ms (build) → 1 856–1 924 ms (seed only) → 530 ms (seed + perf-a shim)**; ACF tags, loop tags and WP-provider tags identical across all runs. One probe transient escaped the write diversion and was deleted immediately (`delete_transient`, confirmed absent).
- PHPUnit `VisualEditorBricksAcfFieldsCacheTest` (11): encode/decode incl. rejection of non-arrays/objects/garbage; store/read with fingerprint + registrars + meta and the size cap; TTL filter with floor; fingerprint memo + salt/extra/registrar-mtime sensitivity + registrar discovery; locale in the transient name; triggers bump once per request and schedule a warm-up; filterable post-type trigger; verify schedule ensure/clear; defaults off + SETTINGS_VERSION 9 + gate refusals without Bricks + nothing written by refused paths; filter veto/force; settings wiring, save path (schedules on enable, clears on disable), actions. Suite **491 / 3 447**; jsdom unchanged; `composer agent-docs:check` passes (six new extension points mapped).

- **Live, after enabling (2026-09-17):** the first capture happened on an admin-ajax request; the daily verify flagged 34 differing fields — every `cta_collection` field's `choices` were DB-populated (Vertical's `vf_populate_cta_collection_choices` hooks `acf/load_field` only when `is_admin()`), whereas every frontend build carries the JSON's static choices. ## 12. Rollback

Untick the switch (schedules cleared; the transient expires by TTL) or delete `AcfFieldsCache*.php` + the `R5.later-perf-b` hunks in `bootstrap.php` / `SettingsPage.php` / `ProviderFingerprint.php`, the three SETTINGS_VERSION assertions and the manifest mapping. The Vertical bridge is a no-op without DBVC.
