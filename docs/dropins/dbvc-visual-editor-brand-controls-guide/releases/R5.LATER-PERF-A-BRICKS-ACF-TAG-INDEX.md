# R5.later-perf-a — Bricks ACF dynamic-data tag-index shim (options A + B)

**Status:** LANDED 2026-09-17 (E-160, D-082). Default **off**. Live equivalence verified on the reference site; the maintainer enables it in Settings → Visual Editor.
**Parent:** R5.later-perf (TTFB root cause E-159, `qa/R5-LATER-PERF-TTFB-INVESTIGATION.md`).

## What it fixes

Bricks rebuilds its ACF dynamic-data tag registry on every frontend / REST request at `init`. On this schema (49 groups, 3 288 nested sub-fields, 2 700 tags) ≈ 1.5 s of that is a quadratic lookup in `Provider_Acf::get_nested_parent_group_field_data()`. This slice ships the same fix two ways:

- **A — upstream:** `qa/R5-LATER-PERF-TTFB/UPSTREAM-BRICKS-REPORT.md` + `bricks-2.3.8-provider-acf-indexed-lookup.patch` (83-line diff, verified on the live site: 1 621 → 52 ms, registry identical). The maintainer submits it to Bricks.
- **B — DBVC shim:** `addons/visual-editor/src/Performance/Bricks/` — an opt-in, fingerprint-pinned, self-verifying replacement of the provider *instance* so the site gets the gain now and can drop the shim when Bricks lands A.

The other ≈ 2 s (ACF's cold field materialisation) is untouched — see option C in the investigation.

## How B works

| Piece | Role |
|---|---|
| `AcfTagIndex` | Pure index: sub-field key → tag names, name → first-insertion position. `lookup()` returns *the first tag in array order whose current sub-fields carry the key* — the stock scan's exact semantics, validated per hit. `referenceLookup()` is the stock scan, kept as the oracle. |
| `IndexedAcfProvider extends Provider_Acf` | Overrides `register_tag()` with a verbatim copy of Bricks 2.3.8's method (GPL, attributed) plus `indexTag()` after each `$this->tags[ $name ] = $tag;`, and `get_nested_parent_group_field_data()` with the indexed lookup. Private-parent calls go through reflection. Never constructed normally (see below). |
| `ProviderFingerprint` | sha1 of the whitespace-normalised source of six Bricks methods read from the installed theme (`register_tag`, `get_nested_parent_group_field_data`, `get_fields_by_context`, `get_flexible_content_parent_layout_data`, `Base::__construct`, `Providers::register`). `KNOWN` pins `07662227…` = Bricks 2.3.8. |
| `AcfTagIndexShim` | Gate + swap + verify + status. |

**Runtime sequence (only when the switch is on):** `after_setup_theme@0` → `arm()`: switch on? Bricks classes present and the private static provider registry accessible? fingerprint known **and** recorded as verified on this site? → hook the swap on Bricks' own registration hook (`bricks/dynamic_data/register_hook`, default `init`) at priority 10000, i.e. after Bricks' `register_providers` (same priority, registered earlier) and before `register_tags` at 10001. `swap()`: the registered `acf` provider must be exactly the stock class with no tags yet and its three constructor filters (`bricks/setup/control_options`, `bricks/query/run`, `bricks/query/loop_object`) at priority 10 — otherwise no-op. Then: create `IndexedAcfProvider` **without running the constructor** (`newInstanceWithoutConstructor` + `adopt('acf')`, so the base constructor's filters are never duplicated), move the three filters from the stock instance to the new one with the same priorities and accepted-args, and replace `Providers::$providers['acf']`. Nothing else in Bricks is touched; `get_tag_value`, loop queries, builder tag lists all run on the new instance with the identical registry.

**Verification (`verify()`):** builds the registry with a stock provider and with the indexed one and requires `tags` and `loop_tags` to be `===` (keys, order, values). Runs on settings save when the box is ticked (records the fingerprint as verified or as `failed:<fp>`), and on demand. The gate refuses to arm unless the recorded fingerprint equals the current one — so a Bricks update flips the shim off by itself until it is re-derived and re-verified.

**Contexts:** admin (Bricks registers no providers → `no_acf_provider`, no-op), REST/AJAX/frontend/builder (providers registered → swap applies; output identical).

## Safety review

- **No behaviour change by construction:** the only altered method is a search whose result is proven equal to the stock scan (property test replaying 120 000 lookups against the oracle; live `verify()` on 2 700 tags + 183 loop tags: 0 differing records; rendered sample tags identical).
- **Fails closed:** any of — switch off, filter veto, Bricks absent, registry shape changed, fingerprint unknown, not verified, provider already replaced by someone else, tags already registered, filters not where expected, exception during swap — leaves the stock provider in place. `state()` names the reason; the settings help text shows `gate` and verification status.
- **No runtime writes.** The only write is the verification marker on settings save / explicit verify.
- **Kill switch:** untick the box (or `wp option update dbvc_visual_editor_bricks_acf_tag_index_enabled 0`). Effect is immediate on the next request.
- **Not gated on the Visual Editor master switch** — deliberately site-wide (help text says so), because every request pays the cost, not just editor requests.

## Enable + verify (maintainer)

1. Settings → Visual Editor → **Performance — Bricks compatibility (site-wide)** → tick **Index Bricks ACF dynamic-data tags** → Save. The save runs `verify()`; the help text then reads `gate: ready · verification: passed for 07662227…`. If it reads `FAILED` the switch stays on but the shim never arms — report it.
2. Confirm on the front end / REST (any logged-out request): `curl -k -o /dev/null -s -w '%{time_starttransfer}\n' https://dbvc-codexchanges.local/wp-json/` — expect ≈ 4.1 s → ≈ 2.6 s on this site.
3. Anytime: `wp eval 'echo json_encode(\Dbvc\VisualEditor\Performance\Bricks\AcfTagIndexShim::status());'` and `wp eval 'echo json_encode(\Dbvc\VisualEditor\Performance\Bricks\AcfTagIndexShim::verify());'` (read-only unless `verify(true)`).
4. After a Bricks update: `status()` shows `gate: fingerprint_unknown` — the shim is inert. Re-pin: derive the new fingerprint (`ProviderFingerprint::current()`), diff `register_tag()` against the vendored copy, update `IndexedAcfProvider` if needed, add the hash to `KNOWN`, run `verify(true)`.
