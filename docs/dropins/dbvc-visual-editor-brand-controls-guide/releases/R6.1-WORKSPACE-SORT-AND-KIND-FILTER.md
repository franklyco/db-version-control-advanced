# R6.1 — Site Manager Workspace: sort-by + Posts / Taxonomies filter

**Status:** CODE COMPLETE + LIVE-QA'D 2026-09-16 — R6.1-a (E-155), R6.1-b (E-156), R6.1-c (E-157; one defect fixed: persisted kind-only selection). Maintainer sign-off over checklist rows 21–26 pending. Maintainer decisions (2026-09-16): "Content" label · no "Most used" · sort is per-workspace view state.
**Parent:** R6 Frontend Site Manager Workspace (code complete, E-142–E-152). Extends `R6-WORKSPACE-STATE-CONTRACT.md` §2/§3/§4/§7 and the R6-A read model (E-142). No new routes, no writes.

## Why

The live site exposes **41 navigable types** (26 post types + 15 taxonomies) in one horizontally scrolling tab strip, and results only ever arrive in "recently modified" order. Two gaps users hit immediately:

1. **"Show me just the taxonomies / just the content"** — today that means scrolling the strip to find a tab. A kind filter collapses the strip to the relevant half and maps 1:1 onto the read model's existing `objectType` parameter.
2. **"Find it by name / see what's newest / what changed last"** — different jobs want different orders. Today's order (modified DESC, relevance when searching) is right for "what did I just touch" and wrong for browsing a type alphabetically.

## Sort options (the set that earns its place)

| Key | Label | Posts (`WP_Query`) | Terms (`get_terms`) | When it's the obvious choice |
|---|---|---|---|---|
| `recent` (default) | Recently updated | `modified DESC, ID DESC` | `term_id DESC` (newest created — terms have no modified date) | "What did I / the team touch last" — today's behaviour, unchanged |
| `title_asc` | Title A → Z | `title ASC, ID ASC` | `name ASC` | Browsing a type you know by name; the single most requested order in every CMS list |
| `title_desc` | Title Z → A | `title DESC, ID DESC` | `name DESC` | Symmetry; cheap once A→Z exists |
| `newest` | Newest first | `date DESC, ID DESC` | `term_id DESC` | "What was added recently" (publish date, not edit date) |
| `oldest` | Oldest first | `date ASC, ID ASC` | `term_id ASC` | Finding legacy content / the original items of a type |
| `relevance` | Best match | `relevance` (string form only) | `name ASC` (WP has no term relevance) | **Only offered while a search term is present**; auto-selected when the user starts typing with `recent` active, restored when the search is cleared |

Deliberately **not** included: `menu_order` (pages only, meaningless across types), `comment_count`, `author`, "most used" for terms (`count DESC` — today's browse default for terms; it disappears in favour of `recent`/`title` because "most-used" isn't a navigation intent). Every key has an `ID` tiebreaker so offset pagination stays stable (R6-A invariant); `relevance` keeps WP's own `post_date` tiebreak.

## Kind filter (Posts vs Taxonomies)

Three-state segmented control **All · Content · Taxonomies** above the type strip:

- `All` → `objectType=all`, subtype `''`, type strip shows every type (today).
- `Content` → `objectType=post`; type strip shows only post types; the strip's own "All" tab means "all content types".
- `Taxonomies` → `objectType=term`; type strip shows only taxonomies.

Selecting a kind resets `subtype` to `''` and re-queries. Selecting a specific type tab implies its kind (existing behaviour). Labels are i18n keys (`workspaceKindAll`, `workspaceKindContent`, `workspaceKindTaxonomies`); "Content" rather than "Posts" because the live site's users think of pages/listings/services as content, not posts — the contract's status chip already says "Page"/"Service".

## UX placement (mockup-consistent)

```
__sticky
  __search-wrap            [ Search… ] [×]
  __controls               [All | Content | Taxonomies]   Sort: [Recently updated ▾]
  __types (tablist)        All · Pages · Posts · Projects …   (filtered by kind)
```

- Kind = `role="radiogroup"` segmented control, same component as the Preferences popover (`__segmented`/`__option` pattern, emphasis tokens) — no new visual language.
- Sort = native `<select>` styled on the control-surface token (5–6 options; a select is the densest accessible control at 480px and reads correctly to AT). Label text "Sort" visually hidden, `aria-label` present.
- Status line copy gains the order when not default: "Showing 20 · A → Z · more available".
- Sticky strip grows by one 32px row; the results region shrinks accordingly (no other layout change).

## Contract deltas

- **State (§2):** `kind: 'all'|'post'|'term'` (alias of `activeType.objectType`, kept as one source of truth — `activeType` stays canonical), `sort: 'recent'|'title_asc'|'title_desc'|'newest'|'oldest'|'relevance'`.
- **Actions (§3.1):** `kind` (+ `data-dbvc-ve-workspace-kind`), `sort` (change event on the select).
- **Persistence (§7 / D-070):** `dbvc-ve-workspace:v1` gains `sort`; `kind` is already persisted via `activeType.objectType`. `relevance` is never persisted (it is search-scoped) — persist the last non-relevance sort.
- **API client:** `searchObjects(search, objectType, { …, sort })`.
- **Route (R6-A, backward-compatible):** `sort` param whitelisted in `ObjectNavigationReadModel::normalizeArgs`; unknown → `recent`; echoed in `query.sort`. Popover fallback keeps sending no `sort` and therefore keeps today's order — D-073 unaffected.

## Backend

`ObjectNavigationReadModel`:
- `normalizeArgs` → `sort` whitelist; `relevance` requested without a search term degrades to `recent`.
- `searchPosts` → `orderby` map (array form for everything except `relevance`, which must stay a bare string — WP_Query ignores it in array form, E-142).
- `searchTerms` → `orderby`/`order` map (`name`, `term_id`); `count` no longer used.
- `mergeObjectItems` interleave unchanged (sort applies within each stream; the interleave is deliberate and documented in R6-A).

Tests (`VisualEditorObjectNavigationTest`): per-key ordering with ID tiebreak; `relevance` without search → `recent`; unknown key → `recent` + echo; pagination non-overlap under `title_asc` across 3 pages; term ordering for `newest`/`oldest`/`title_*`.

## Frontend

`workspace-app.js`: `state.sort`, `state.kind` derived; `createControls()` in the sticky strip; `setKind()` / `setSort()` → persist + `runSearch()`; `renderTypes()` filters `types[]` by kind; search input `input` → if `sort === 'recent'` and the term becomes non-empty, switch to `relevance` (and back on clear); `statusText()` order suffix. `navigate()` API accepts `sort`/`kind`.

jsdom (workspace suite): kind filter narrows the strip and sends `objectType` with empty subtype; sort select sends `sort`; relevance auto-toggle on type/clear; persisted sort restored; `relevance` never persisted; status suffix.

Mockup: add S-20 (kind + sort controls) to `states.html` + a DESIGN-DECISIONS entry (segmented kind, native select sort, relevance rule) — a small D2-style update, no new D1–D4 cycle.
