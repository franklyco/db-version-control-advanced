How the simple version maps to the engine

For reviewers and engineering · not a product screen

Design rules

Smart by default.

Three questions at setup, every default already chosen (everything both sites report, hourly, report-only, values on, daily summary). Nothing technical is required to get a working watch.

Changes appear as they are recorded, not as "reports".

The product surface is an inbox of objects. Each hourly pass adds items to it; a "new since you last looked" line marks arrivals. Runs, cycles and report ids exist only in the full console.

One decision per item, in words.

"Done" and "Leave it" replace reconciled / ignored. Verification is automatic and silent; only "still differs" or "changed again" bring an item back.

Drill-down is always one click away, never in the way.

"Show technical names" per item, the Advanced block in Settings, and "Open full console" to the agency view. The simple view hides; it never removes.

Never applies anything.

No "use staging's version" button. The user edits LocalWP themselves, then says Done. Releases and approvals stay in the full console (publisher role).

Review questions for this version

  1. (e) Inbox-first (objects accumulate, runs are invisible) versus the run-based Reports list — is there any case where an operator needs "what did the 11:00 pass find" in the simple view?
  2. (f) Wording of the two decisions: "Done" / "Leave it" — or "Updated" / "Ignore"?
  3. (g) "Remind me tomorrow" adds a snooze state. Keep (tiny) or drop (the item just stays open)?
  4. (h) Setup pairs both sites from the hub. Should the LocalWP plugin page instead be the entry point ("Connect this site to staging") for a studio user who never opens the hub?
  5. (i) Conflicts: "Sorted" implies the user re-aligned LocalWP by hand and re-baselines the object silently. Acceptable, or should it ask "which one is right?" first?
