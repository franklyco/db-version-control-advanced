## 1. Why / goal

A studio builds a client site on LocalWP, copies it to Cloudways staging, and runs a VerticalFramework **Design Review** round there (`functions/features/design-review/` in the theme: pins anchored to Bricks elements, exported as `vf-design-review/1` JSON; it never edits Bricks data and never syncs installs). The studio then edits the **staging** copy to address the feedback. Nothing carries those edits back, so the LocalWP build silently diverges until someone exports, zips, uploads and reads a core DBVC proposal by hand.

**Goal:** an automated, read-only pipeline that tells the LocalWP operator, per object, *what changed, what was added and what was removed on staging since the copy was made* — with the changed fields and both sites' values — on a schedule, with no apply, no merge and no new write path to either site; plus a review flow so the operator can work the list down (reconciled by hand, intentionally different, or promoted into a real guarded release).

**Not goals:** applying or merging automatically (bidirectional parity stays out of scope by design, `connected-environments-agency-control.md` §Out of scope); replacing core export/import; a UI inside Design Review; covering domains Connected Environments does not observe (§8).

**Core DBVC is a full-state mirror plus a manual review tool, not a change log.**

Options, menus and options groups are not diffed (`:5898-5928`).
- `wp dbvc export --baseline` (`includes/class-sync-posts.php:4774-4904`) is posts-only, single-site, no deletion detection.

**Connected Environments (CE) already has the automated half.**

The connector keeps the latest canonical body in `dbvc_ce_objects.snapshot_body` (CE `Storage/Schema.php:208-228`) — latest only, no history.

## 3. Gap, stated precisely

| Need | Today | Gap |
|---|---|---|
| Detect per-object created / updated / removed on staging | Hash + exists per event; removal observed; `compare` classifies | No `created/updated/removed` label; nothing runs `compare` unattended except `auto` parity |
| Show *what* changed | Prepare receipt: top-level keys, hashes, staging value (hub-side render) | No nested paths, no local (target) value, no connector-side redaction of local values, no receipt size cap |

| Deliver it to the operator | Hub CLI/admin; `site.drifted` is framework-only | No "report ready" notification; no LocalWP-side view; no markdown/JSON hand-off |
| Coverage of what Design Review edits touch | Bricks templates/classes/variables/components (opt-in), pages/posts (opt-in) | ACF options pages, terms, menus, media not observed (§8) |

## 4. Design overview

**Reuse the release → prepare dry run as the transport, add a nested two-value diff to the receipt (redacted on the connector), and wrap it in a `report` policy mode that runs on the parity tick, dedupes its own release, recovers from payload mismatch, and never approves.** On top sit a durable report with per-object review decisions, a notification, and (optionally) a LocalWP-side view.

```
STAGING (source connector)        HUB (agency-control)                                LOCALWP (target connector)
 observe edits ──events──▶  projections (hash/exists)                     ◀──events──  observe edits
                            parity tick (SchedulerRunner / WP-Cron):
                              policy mode=report, cadence hourly
                              ComparisonService.compare(staging, local)
                              ├─ either side stale → report run "stale", no release
                              ├─ comparison digest unchanged → "no change", no release
                              └─ propose ONE tracked release (purpose=report):
                                   outgoing → replace · outgoing+absent → delete
                                   conflict → replace · target-absent → create
 ReleaseWorker uploads   ──▶  release_items.payload
 bodies from snapshot_body     mismatch → withdraw + re-propose next tick
                              sealed → PreparationService.request(local)  ──poll──▶  Preparer dry run (live read)
                                                                                      BodyDiff(local, staging)
                              ◀── prepare receipt (nested paths, both values,   ◀──   ReceiptRedactor (masks + key patterns + truncation)
                                  redacted, size-capped)
                              ChangeReportService: comparison rows + receipts
                                → dbvc_ac_change_reports / _items (durable)
                                → decisions carried forward (reconciled / ignored / promoted)
                                → notification report.generated
                              purge report-purpose releases + preparations after retention
                              hub admin "Reports" section · CLI · REST · (LocalWP "Reports" tab via machine-REST read)
                              NEVER approve in report mode; LocalWP apply gate stays off
```

Design Review stays where it is. Its JSON export is an annotation source for the report (CR-6, shipped).

## 5. Decisions (recommended)

| # | Decision | Choice | Why / alternative rejected |
|---|---|---|---|
| D1 | Where bodies live | In `dbvc_ac_release_items.payload` as today, but **report-purpose releases are purged** after the report row is built and the retention window passes (new `ReleaseService::purge(purpose='report', older_than)` deleting release, items, preparations, approvals; media blobs via existing GC) | Verified: nothing prunes releases today, so an hourly report mode would accumulate payloads indefinitely. A permanent content-addressed body store on the hub is still rejected (the hub would become a content store). The purge is scoped to `purpose='report'` so operator releases are untouched. |
| D2 | Diff engine location | New pure class `Dbvc\ConnectedProtocol\BodyDiff` in `includes/Dbvc/ConnectedProtocol/` | Shared by connector (Preparer) and hub (report renderer); protocol classes are loaded by core (`db-version-control.php:182`). Generalizes `Preparer::patch` from top-level keys to dot-paths; mirrors core `compare_snapshots` labels. |
| D3 | How a report run is triggered | New sync-policy `mode=report` driven by `SyncDriver` on the parity tick; **tracked** like `auto` (`active_release_uid`), with a `report` branch in `select_objects`, `sync_now`, `advance`, `require_policy` and the `ParityScheduler` filter | Verified: `assisted` is never ticked and never deduped, so it is not a usable base. Tracking the release is what prevents one release per tick. |
| D4 | Selection in report mode | `outgoing` (+complete) → `replace`; `outgoing` + source absent → `delete` (always, ignoring `propagate_deletions`); `conflict` → `replace` (always, ignoring `conflict_policy`; nothing applies); `baseline_required` + target absent → `create` (always, ignoring `create_new`); `incoming`, target-locked and `unknown` rows are **listed hash-level** in the report but not transported | A report must show conflicts and removals; the apply-side policy flags are meaningless when nothing applies. LocalWP-only changes need no transport (the operator made them). |
| D5 | Stuck-release recovery | In report mode, `advance` treats any `mismatch` item on the active release as **withdraw + clear state**; the next tick re-proposes with current hashes; after 3 consecutive mismatch cycles the run is recorded `unstable_source` and notified | Verified: a source edit between propose and upload leaves the release open forever. Staging is under active edit during Design Review, so this is the normal case, not an edge. |
| D6 | Values on the wire | Connector-side setting on the **target** (`dbvc_connected_receipt_values`, default off): when on, the Preparer emits `before_value`/`after_value` per path through a new `ReceiptRedactor` (DBVC mask list + the existing key-pattern rule + 200-char truncation, matching `format_incoming_value`); over a new hub receipt cap (`MAX_RECEIPT_BYTES`, 1 MiB) → paths only, `values_omitted=true` | Verified: no release-level flag exists and adding one needs a schema column; the hub stores receipts verbatim, so redaction must happen on the connector; Bricks collections are unmasked at projection. Keeping the switch on the target means the LocalWP operator decides whether their values leave the site. |
| D7 | Batch size | Report-mode cycle cap 50 objects (policy `max_objects` default raised for `report`); the prepare-requests GET is paged to stay under the connector's 1 MiB response cap; a report **run** spans as many releases as cycles it takes, and the report row lists them | Verified binding limits are `max_objects` (25) and the 1 MiB inline-bodies response, not `MAX_RELEASE_ITEMS` (200). |
| D8 | Durability | New hub tables `dbvc_ac_change_reports`, `_report_items`, `_report_decisions` — one schema bump 20 → 21 shared by CR-2 (`releases.purpose`) and CR-3; `table_names()` updated; manifest/snapshot docs updated per the v19→20 precedent. (Shipped as 21 → 22; CR-4e added `_report_run_items`, 22 → 23.) | Receipts and payloads are release artefacts that D1 now purges; the report is the artefact the operator works from. |
| D9 | Change labels | Derived at report build from the comparison row + receipt: `created` (create item), `updated` (replace, `outgoing`), `removed` (delete), `conflict` (replace, `conflict`), `local_only` (`incoming`, hash-level), `converged`, `locked`, `unknown` | No change to `ObservationEvent` v0.2 (bumping `schema_version` rejects un-upgraded connectors). |
| D10 | Baseline semantics | `baseline-confirm` once right after the clone enrolls; reports are "since baseline"; a **decision** (D11) may re-confirm baseline for that one object | Auto-advancing the baseline would hide unreconciled changes. |
| D11 | Review decisions | Per pair + domain + instance, persisted across reports with the `decided_hash` pair: `reconciled` (operator ported it by hand; next tick verifies `converged`/`synchronized` and marks it `verified`, optionally confirming baseline for that object), `ignored` (intentional divergence; stays muted until the staging hash changes again → reopens as `changed_again`), `promoted` (selected into a real staging→local release that goes through the existing prepare → approve → guarded apply; needs the LocalWP apply gate on) | This is the "approval and review flow": nothing is applied by the report itself, but every item has a way to leave the list, and the loop closes without a merge engine. Decisions are approver writes; promote is a publisher write. |
| D12 | Stale handling | A run with either side stale records `stale_source`/`stale_target`, creates no release, surfaces the last **seen** time, and notifies once per stale episode. **CR-4d:** "stale" = not heard from at all (no poll and no observation) inside the freshness window; a quiet site that still polls is live and its projections current, so it is not stale | Honest-states principle (admin-page §2.1); a stale pair must not read as "in sync" — and a healthy quiet site must not read as stale (CR-4c live finding). |
| D13 | Topology | The existing agency hub (both sites outbound-only to it) | Co-locating the hub on the Cloudways install is plausible but unverified (loopback REST). Hubless file mode is CR-5, a fallback. |
| D14 | Where the operator reads it | **Decided 2026-11-08 (CR-M a, h):** one hub-served **Site Changes** page per pair — the simplified inbox by default, the advanced console as drill-down — linked from both the staging and the LocalWP connector page. No separate LocalWP-side Reports tab and no connector-side wizard; setup lives on the hub. The machine-REST read `GET /reports?target=me` is therefore not needed for CR-3; it stays optional (CR-3c) | The LocalWP operator works on LocalWP; walking to the hub for every item is friction. The machine-REST read is the first connector-visible report surface, so the mockup must justify it. |

4. ### CR-4d — poll heartbeat: freshness follows liveness (hub; no schema) — SHIPPED 2026-11-19

| Area | Change |

## 9. Safety / governance

- Read-only by construction: `report` mode never calls approve; the LocalWP apply gate stays off; `ReleaseWorker` refuses apply without the gate. *Promote* creates an ordinary release that goes through the unchanged prepare → approve → guarded apply path.
- No new inbound surface on any connector; hub additions are reads (either cap), decision writes (approver), promote (publisher), one optional machine-REST read.
- Content exposure: staging bodies reach the hub as today (release payloads) but are now **purged**; LocalWP values leave the site only with the target-side setting on, redacted on the connector, size-capped on the hub.
- Complies with the CP-F7 rule (detection-only, no automatic apply) and the "no permanent hub-write rule" operator note.
- `docs/agents/MAINTENANCE.md` at implementation time: new CLI/REST/table/setting records, `composer agent-docs:check`.
