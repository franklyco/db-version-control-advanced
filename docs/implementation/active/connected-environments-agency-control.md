## What is implemented (M1 slice)

### Module boundaries

- `addons/connected-environments/bootstrap.php` — `DBVC_Connected_Environments_Addon`. Gate option `dbvc_addon_connected_environments_enabled` (default `'0'`), kill switch constant `DBVC_CONNECTED_EMERGENCY_DISABLE`, single-site only. Disabled: registers the `Dbvc\Connected\` autoloader and two exclusion filters, nothing else — no tables, options, cron events, listeners, routes or assets. The gate option is not even created until the settings page or a save touches it.
- `addons/agency-control/bootstrap.php` — `DBVC_Agency_Control_Addon`. Gate `dbvc_addon_agency_control_enabled`, kill switch `DBVC_AGENCY_EMERGENCY_DISABLE`. Enabled runtime is `Dbvc\AgencyControl\Runtime::boot()` returning `scaffold_only` with every capability `false`; it registers nothing and needs neither the connector, Bricks nor the Visual Editor.
- `includes/Dbvc/ConnectedProtocol/` — shared pure contract layer loaded through its own lazy autoloader (`autoload.php`, required by the main bootstrap): `Canonicalizer`, `CanonicalizationException`, `ObservationEvent`, `RoleGate`, `Comparison`, `DomainObserver`.
- Settings UI: one "Connected Environments" subtab under Configure → Add-ons with both gates and a read-only status table (rendered only when the connector gate is `ready`).

### Canonicalization contract (version 1)

Lists (keys `0..n-1`) keep order; every other array/object is a map with byte-order sorted keys; `[]` encodes as an empty list (PHP cannot express an empty map — pass `stdClass` for `{}`); `null`, booleans, integers native; floats shortest round-trip with a preserved fraction (`1.0`); strings must be valid UTF-8 (rejected, never substituted), unescaped slashes/unicode; non-finite floats rejected; only caller-listed top-level volatile keys are stripped (none for the two Bricks profiles). Missing key, `null`, `""`, `[]`, `{}` and `false` all hash differently. Profiles: `bricks-global-class-v1`, `bricks-variable-v1`, `bricks-collection-order-v1`. Absent objects use the hash of canonical `null`; incomplete projections use the hash of canonical `false` with `complete=false`.

### Capture (save side)

`OptionSignalListener` hooks `updated_option`, `added_option`, `deleted_option` (one array lookup for unrelated options). A watched option maps to one dirty key per domain (`collection`). `JobStore::mark_dirty()` is a single `INSERT … ON DUPLICATE KEY UPDATE generation = generation + 1`; `available_at` is set on first signal only (`LEAST`), so bursts coalesce without starving. One `wp_schedule_single_event(dbvc_connected_process_observations)` is scheduled when none is pending (delay `dbvc_connected_processing_delay`, default 20 s). No network, no option values, no identity assignment on save. Measured in the lab: +2.1 queries and ≈ +1.3 ms per watched save (3-class fixture).

### Worker (background)

`ObservationWorker::run()` (cron hook or `wp dbvc connected process`): claims due markers with a compare-and-set lease and captures `claimed_generation`; reads the whole collection once through `BricksOptionCollectionObserver` (direct persisted row read, bypassing object cache and `option_*` filters); inside one transaction (`START TRANSACTION`, or `SAVEPOINT` under the `dbvc_connected_transaction_strategy` filter used by the PHPUnit harness) it assigns missing instance identity (`InstanceIdentity::assign()` — the only identity writer), emits an event for each new/changed member, emits tombstones (`exists=false`) only after a complete read, emits a separate collection-order projection (`instance_uid=collection.order`), then acknowledges with `DELETE … WHERE lease_token = ? AND generation = claimed_generation`. `generation_advanced` releases the lease and keeps the marker pending; `lease_lost` rolls the whole transaction back. Sequence allocation is `UPDATE … LAST_INSERT_ID(next_sequence)+1`. Events are `agency-control.observation.v0.2` bodies validated before insert; event id `obs-<12-digit sequence>`, unique on `(epoch, event_id)` and `(epoch, sequence)`. Unchanged members emit nothing. Unavailable Bricks (`dbvc_connected_bricks_available` false) holds the marker with a backoff and never produces tombstones. Duplicate storage keys fail closed for the affected members and mark the inventory incomplete.

### Identity and lifecycle

- Provisional environment identity (`local-<hex>`, epoch `provisional-<date>-<hex>`) is created explicitly when the connector is enabled (`StateStore::initialize_provisional()`); re-enabling never rotates it. It is not network authority (M2 binds or replaces it).
- Enabling from a disabled state requests a `reconciliation` of every supported domain (`origin=reconciliation`, `causation_id=enable`); `wp dbvc connected reconcile` does the same on demand.
- Disabling unregisters listeners and clears the scheduled event; stored observations are retained.
- `TransferExclusions` excludes gate options and `dbvc_ce_*`/`dbvc_ac_*`/`dbvc_connected_*`/`dbvc_agency_control_*` keys from `export_options_to_json()` and from `import_options_from_json()`.

### Inspection

`wp dbvc connected status|jobs|objects|outbox|inventory` (read-only; `inventory` reports `identity_missing` instead of assigning) and `reconcile|process` (management writes). Status distinguishes `never_observed`, `pending` and `observed` per domain so an empty object set is never a clean claim.

## What is implemented (M2 step 1: enrollment + receipt + outbound delivery)

### Authentication decision (ADR-009 resolved)

WordPress Application Passwords, one restricted service user per enrolled environment. `EnrollmentService::exchange()` creates a user in the capability-less role `dbvc_connected_environment`, creates one application password (`WP_Application_Passwords::create_new_application_password`), and binds `(user_id, app_password_uuid)` to the environment row. Machine routes resolve the principal with `rest_get_authenticated_app_password()` + `get_current_user_id()` and look it up in the registry; an administrator cookie session or an unbound application password gets 401/403. Revocation deletes the application password and marks the environment revoked. The Bricks HMAC primitives (`DBVC_Bricks_Command_Auth`) were not reused: client-role coupled, option-array nonce store, tied to `dbvc_bricks_*` settings. Application passwords require HTTPS or `WP_ENVIRONMENT_TYPE=local` (labs).

### Hub (`addons/agency-control/`)

- Stores (schema v1, created by the enable lifecycle): `dbvc_ac_invitations` (SHA-256 of the token only, expiry, single-use consumption), `dbvc_ac_environments` (agency/client/environment, hub-assigned `current_epoch`, principal binding, `status enabled|held|revoked`, enrolled/last site URL, receipt counters), `dbvc_ac_events` (UNIQUE `(environment, epoch, event_id)` and `(environment, epoch, sequence)`, digest, immutable body, `routing_state=pending` persisted with receipt as the durable routing job for step 2), `dbvc_ac_projections` (per object/profile, updated only by a higher sequence).
- Routes (`dbvc-agency/v1`): `POST /enrollments/exchange` (token is the authority; returns the credential once; the hub assigns `enrolled-<date>-<hex>` as the epoch; fixed invitation ids override the proposed id; collisions 409; unsupported protocol 409), `POST /observations` (≤50 events / ≤256 KiB; per-event `accepted|duplicate|conflict|rejected` with reasons `already_received`, `event_digest_mismatch`, `sequence_reuse`, `epoch_mismatch`, `environment_mismatch`, `invalid_event:*`; sender-supplied `recipients`/`client_id`/`agency_id` fields fail validation; `origin=apply` is stored as an ordinary observation), `GET /capabilities`.
- Site-URL drift: the `X-DBVC-Site-URL` header is compared with the enrolled URL; a mismatch holds the environment (`409`, `site_url_mismatch`) until `wp dbvc agency release`, which adopts the reviewed URL. Revoked environments cannot be released.
- CLI: `wp dbvc agency status|environments|events|projections` (read-only) and `invite|revoke|release|hold` (A2: `hold --reason` records an operator hold; `invitations [--open]` lists invitations without tokens).

### Connector (`addons/connected-environments/`)

- Schema v2 adds enrollment columns to `dbvc_ce_state` (hub URL, agency/client ids, principal, sealed secret, `connection_state disconnected|enrolled|held`, hold reason, enrolled site URL, delivery status). `SecretBox` seals the credential with a key derived from `wp_salt('auth')` (libsodium, OpenSSL AES-256-GCM fallback); a database copied to an installation with different salts cannot open it and delivery holds with `credentials_unreadable`.
- `EnrollmentService::exchange(hub, token)` posts the proposed environment id, site URL and supported protocol versions; on success it adopts the hub identity/epoch, **restarts the sequence allocator at 1**, marks every pending outbox row of other epochs `superseded` (immutable history is never rewritten), and requests a reconciliation so the current state is re-emitted under the new epoch (the observer treats a different `observed_epoch` as changed).
- `HubClient` uses `wp_remote_post` to `{hub}/index.php?rest_route=/dbvc-agency/v1/…` (works without pretty permalinks, no redirects), TLS verify on, 10 s timeout, Basic auth, `X-DBVC-Site-URL`/`X-DBVC-Protocol` headers; plain `http://` only for `local` environment type or the `dbvc_connected_allow_insecure_hub` filter.
- `OutboundWorker` (cron `dbvc_connected_deliver_outbox`, scheduled when the observation worker emits events while enrolled, or `wp dbvc connected deliver`): leases pending rows of the current epoch in sequence order (≤50, ≤256 KiB), settles each from the hub outcome (accepted/duplicate → `delivered` with receipt; conflict/rejected → `rejected` with reason), releases unanswered rows with exponential backoff, and holds the connection on 401/403/409 or `epoch_mismatch`. `wp dbvc connected resume` clears operator-reviewable holds; credential/epoch holds require re-enrollment.

## What is implemented (M3 step 1: baselines and three-way comparison)

- Hub schema v3: `dbvc_ac_baselines` (source, target, domain, source/target instance UID, profile → `baseline_hash`, agreed sequences/epochs, confirmed_by/at, note; unique per pair/object/profile) and `dbvc_ac_instance_links` (operator-declared lineage between an instance on the source and one on the target; unique in both directions).
- `ComparisonService::compare(source, target[, domain])` (read-only): loads both environments' current-epoch projections, pairs by explicit link else equal instance UID, derives per-domain coverage from a complete `collection.order` projection (Bricks) — `wp.service` has none, so a never-observed target object stays `unknown` (`target_coverage_unknown`) — treats a missing row inside complete coverage as verified absent, applies freshness (`dbvc_agency_control_freshness_seconds`, default 24 h since last authenticated contact; non-enabled environments are never fresh) and completeness, then classifies with the pure `Comparison::environment()`: `synchronized|outgoing|incoming|converged|conflict|baseline_required|unknown`, plus reasons, `source_observed`/`target_observed`, hashes and sequences. Both sides absent → `synchronized (both_absent)`. Scope: same agency/client, not self.
- `BaselineService::confirm()` is the only baseline writer: rows in `converged` state, or `baseline_required` with equal hashes, that are complete and fresh; `--accept-absent` additionally records an absent baseline when exactly one side is verified absent (declaring "the other side never had this"), after which the row classifies as outgoing/incoming. Skips report `no_agreement`, `not_complete_or_fresh` or `unknown:<reasons>`. Receipt, routing, delivery and acknowledgement never create or advance a baseline.
- CLI: `wp dbvc agency compare --source --target [--domain] [--state]`, `baseline-confirm [--domain] [--instance] [--note] [--accept-absent]`, `baselines`, `link-instance`, `unlink-instance`, `links`; `status` adds baseline count and freshness policy.
- Findings from the lab: independently enrolled environments generate different Bricks sidecar UIDs, so without a link each class appears as unobserved on the other side (the CLI shows this via the observed flags); linking pairs them and confirmation records the agreement. Independently *created* service posts do not agree because `post_date_gmt` differs — DBVC-imported copies preserve the date, so synced content pairs naturally.

## What is implemented (M3 step 2: framework definitions, adoption, overrides, framework status)

- Hub schema v4: `dbvc_ac_definitions` (agency, definition UID, version label, studio-supplied `version_order`, channel, domain, profile, `definition_hash`, `desired` flag, optional source environment/instance, publisher, note; unique per `(agency, definition, version)` and per `(agency, definition, channel, version_order)` so version distance is never ambiguous), `dbvc_ac_overrides` (environment, domain, instance, definition → `approved_hash`, `definition_version` at approval, frozen `policy_revision` from the routing registry snapshot, `state approved|needs_rebase_review|detached`, rationale, approver; unique per instance/definition), and `adopted_version` + `channel` on framework subscriptions.
- `FrameworkService` (explicit studio actions only): `publish()` records an immutable version — hash supplied, read from one environment's current-epoch projection (only if enabled, fresh, complete and existing), or copied from a published version with `from_version` (so a beta hash can be re-published on `stable`); re-publishing a label is refused (`dbvc_agency_definition_exists`), a taken order is refused (`dbvc_agency_version_order_taken`), and the order defaults to one past the highest published order — labels such as `1.10`/`1.9` are never compared. `set_desired()` moves a channel's desired version and flags that channel's `approved` overrides `needs_rebase_review` (never rewriting or removing them). `adopt_version()` declares the version a subscription follows (must be published, same domain). `approve_override()` needs a framework subscription and a rationale, takes the exact hash explicitly or from the environment's current projection, and freezes the policy revision; `detach_override()` ends it.
- `FrameworkStatusService::status()` (read-only): for every enabled framework subscription, the environment's current projection hash (only when fresh and complete) against the adopted definition hash, the channel's desired version and any non-detached override, through the pure `Comparison::framework()`; `version_differs` is refined with `version_order` into `behind_version` / `ahead_version`, or `channel_mismatch` when the adopted version lives on another channel. Missing adoption, missing desired version, unknown adopted label, missing environment, stale contact, never-observed or incomplete projections all report `unknown` with reasons; counts include `rebase_review`. Nothing here changes content, adoption, definitions or overrides.
- CLI: `definition-publish`, `definition-desire`, `definitions`, `adopt-version`, `override-approve`, `override-detach`, `overrides`, `framework-status [--environment] [--definition] [--drift]`; `subscribe-framework` gains `--adopted-version`/`--channel`; `subscriptions` shows both; `status` counts definitions and overrides.
- Semantics kept from the package (and from the Bricks add-on review): an override is an exact approved hash, so a later client change to an overridden object is visible as `override_changed`; a client reverting an override to the framework hash still reads `override_changed` (the approval no longer describes what is deployed) until the studio detaches it.

## What is implemented (M5 step 1: one guarded round trip)

- Hub schema v8: `dbvc_ac_approvals` (approval UID, prepare operation id, release + digest, receipt digest, target environment + epoch, policy revision, `approved|consumed|revoked`, note/approver, `expires_at` = the receipt's expiry, execution outcome/receipt/digest). `ApprovalService::approve(operation_id)` accepts only a received prepare receipt whose outcome is `ready` or `noop`, unexpired, for a sealed release, an enabled target still on the receipt's epoch, with no earlier approval, and whose before-state agreed with the hub's last projection of the target (`dbvc_agency_receipt_disagrees` otherwise — the target must report first). `revoke()` withdraws an unconsumed approval. `pending_for_target()` (route `GET /releases/apply-requests`, target principal, enabled) serves open approvals with the sealed manifest, payloads, the bound receipt and its digest, cancelling approvals whose epoch, release or receipt no longer match. `accept_execution()` (route `POST /releases/{uid}/apply-receipts`) validates operation id, digests, target and outcome, stores the execution receipt with its digest exactly once (the approval becomes `consumed`), and advances the pair baseline (`baseline_hash = after_hash`, note `applied:<operation>`) for every item reported `applied` and `verified`.
- Connector apply gate: `dbvc_addon_connected_environments_apply_enabled` (off by default, refused while the connector is off, cleared when the connector is disabled, excluded from options export/import, shown as a second checkbox in the Add-ons tab). Capabilities advertise `apply` only while it is on; the release worker retrieves approvals only then.
- `Applier` (connector schema v5, `dbvc_ce_operations` journal): binds the approval to the receipt this environment produced (local digest match, receipt canonical hash, release digest and epoch), refuses expired approvals, groups ready items by container (Bricks option collections only in this step; `wp.service` items report `unsupported`), re-reads every container's raw persisted value and refuses the whole container as `stale` when its fingerprint differs from the receipt's, journals the verified before image *before* the first write, re-verifies each member's canonical hash against the receipt's before-hash, builds the new value by whole-object replacement in place (deletions spliced out, unrelated members preserved), writes with one conditional statement `UPDATE … SET option_value = %s WHERE option_name = %s AND SHA2(option_value, 256) = <fingerprint>` (affected rows ≠ 1 → `stale`, nothing overwritten), flushes the option caches, verifies every member through the read-only observer (`applied`/`verified`), and on a failed verification compensates with the same conditional write back to the journalled before image and verifies the restore (`compensated`, or `failed` with `restore_unverified`). A written container is signalled to the observation pipeline with `origin=apply` and the operation id as causation. Execution receipts carry per-item outcomes, fingerprints before/after, the step journal and the warning that Bricks CSS is not rebuilt. A journal row that exists but never finished is reported as `operation_in_progress_recovery_required`, never executed again; an unreported execution receipt is re-sent on the next run, a definitively rejected one kept as evidence.
- CLI: hub `approve --operation [--note]`, `revoke-approval --approval`, `approvals [--approval] [--target]`; connector `operations [--operation]` (journal without the raw before image); `status` counts approvals/operations on both sides.

## What is implemented (M4 step 2: dependency ledger, deletion items, release/receipt views)

- `DependencyLedger` (connector, read-only): for each `ready` candidate the after-state's references are discovered on the target — Bricks members: the category id (`category`/`cat`) against `bricks_global_classes_categories` / `bricks_global_variables_categories`, and every `var(--name)` used in settings/value against the target's `bricks_global_variables` names or another item of the same release (`selected`); service posts: `post_parent_uid` (by `vf_object_uid`, or `selected` when the parent is in the release), each `tax_input` term slug (taxonomy not registered → `unsupported`; term missing → `unresolved` with `term_creation_requires_decision`), and media references in content/meta (`wp-image-<id>`, upload URLs) as `unsupported` (media transfer is not part of prepare). Every entry is `required`; `unresolved`/`unsupported` entries block the item with `dependency_<status>:<kind>:<ref>` while the exact patch is still reported beside the blockers; `complete=false` marks discovery that could not finish.
- Deletion items (hub schema v7 `operation replace|delete` on release items): `release-create --delete=domain:uid` selects a source object the hub holds as a verified absence (tombstone; a present object is refused with `dbvc_agency_projection_present`, and an absent object selected for replacement with `dbvc_agency_projection_absent`). The source connector supplies the canonical `null` as payload only while the object is still absent under the current epoch; the manifest digest includes the operation. On the target, `Preparer` reports `ready` with `remove_object` and the exact before-hash when the object is present, `noop` when it is already absent or was never known (no creation decision is needed to not-create), and never runs dependency discovery for removals.
- Administrator surfaces: the hub panel lists releases (state, items, digest, note, sealed) and prepare receipts (state, outcome, ready/no-op/blocked, requested/received/expires); the connector panel lists the receipts it produced with their reporting state.

## What is implemented (M4 step 1: release manifests, payload transfer, prepare receipts)

- Hub schema v6: `dbvc_ac_releases` (release UID, agency/client, source environment + epoch, `open|sealed|withdrawn`, item count, digest, note, creator), `dbvc_ac_release_items` (domain, instance UID, profile, `after_hash` fixed at creation, source sequence, `payload_state requested|received|mismatch`, the canonical payload, reason), `dbvc_ac_preparations` (operation id, release, target environment + epoch at request, `requested|received|cancelled`, outcome, ready/noop/blocked counts, the receipt with its digest, hub notes, expiry).
- `ReleaseService::create(source, selections)` fixes an immutable manifest from the source's current-epoch projections — each selected object must be complete and exist (deletions are not releasable yet), `collection.order` is refused, the source must be enabled and fresh. `accept_payloads()` (route `POST /releases/{uid}/payloads`, source principal only, same epoch, open release) verifies every body with `Canonicalizer::hash()` against the manifest hash before storing it, records `hash_mismatch` / `source_changed` otherwise, and seals the release (digest over the sorted item list) once every item holds a verified payload. A mismatched release never seals; `withdraw` ends one.
- Connector `ReleaseWorker` (rides the inbox poll schedule, outbound only): answers `GET /releases/payload-requests` with the canonical bodies already recorded in `dbvc_ce_objects` — only while the stored hash still equals the manifest hash under the current epoch and the projection is complete; otherwise it reports `mismatch` with the current hash and never sends a different body. Then `GET /releases/prepare-requests` → `Preparer::prepare()` → the receipt is stored in `dbvc_ce_preparations` (connector schema v4) *before* `POST /releases/{uid}/prepare-receipts`; a receipt the hub could not be reached for is re-sent on the next run, one the hub definitively rejected is kept as local evidence and not resent.
- `Preparer` (dry run, no writes, no identity assignment): per item — payload hash re-verified; observer available and profile matching; identity resolved by portable UID only (Bricks: sidecar `find_by_instance_uid`; `wp.service`: `vf_object_uid` meta, ambiguous → blocked) with the hub's operator lineage links honoured through `target_instance_uid`; current persisted state read through the read-only observer (Bricks `snapshot()` now returns the member's canonical body); outcome `noop` when the before-hash equals the after-hash, `ready` with an exact whole-object patch (`replace_object`, changed top-level paths with per-path before/after hashes, container `option:<name>` / `post_type:<type>#<id>`, container storage fingerprint), or `blocked` with an explicit reason (`identity_unmatched:creation_requires_decision`, `identity_ambiguous`, `identity_missing`, `target_object_absent`, `target_projection_incomplete:<problems>`, `domain_unavailable:<reason>`, `profile_mismatch`, `payload_hash_mismatch`). Receipt outcome `ready|noop|blocked|partial`, compatibility block (protocol, canonicalizer, plugin version, per-domain availability), `expires_at` = prepared + `Protocol::PREPARE_RECEIPT_TTL_SECONDS` (1 h).
- `PreparationService::request(release, target)` needs a sealed release, an enabled target of the same agency/client that is not the source, and no outstanding request for that pair; `pending_for_target()` cancels requests whose release is no longer sealed or whose target epoch moved; `accept_receipt()` (target principal only, one receipt per operation) validates release UID/digest/target/epoch/outcome/item count/timestamps, stores the receipt with its digest, and annotates it with the hub's own view (`hub_target_hash`, `target_projection_agrees`, pair `baseline_hash`, `target_edited_since_baseline`) — annotations add no authority.
- CLI: hub `release-create --source --items=domain:uid,… [--note]`, `release-withdraw`, `releases [--release] [--source]`, `prepare-request --release --target`, `preparations [--operation] [--release] [--target]`; connector `release` (run the worker once) and `preparations [--operation]`; `status` reports release/preparation counts on both sides. Capabilities advertise `release_payloads` and `prepare` (still `apply: false`).

## What is implemented (M3 step 3: service coverage, review resolution, administrator surfaces)

- Connector: `ServicePostObserver` reports a coverage projection for `wp.service` — identity `collection.order`, profile `wp-service-inventory-v1`, the canonical sorted set of portable `vf_object_uid`s of every observed-status post; complete only when the enumeration was full and every post carries a UID (otherwise the incomplete marker hash). It is emitted on reconciliation (through `inventory()['order_hash']`, so an empty service set is a complete fact) and re-read cheaply (IDs and UIDs only, `inventory_projection()`) after every per-object `post:<id>` claim, so adding, trashing or deleting a service changes the inventory row. `ObservationWorker::emit_order_projection()` takes the order profile from the observer's `capabilities()['order_profile']` instead of the Bricks constant. On the hub, `ComparisonService::coverage()` already keys on `collection.order`, so a service never observed on the target inside a complete inventory is verified absent (`baseline_required` → `--accept-absent` → `outgoing`) instead of `unknown`; an incomplete inventory withdraws coverage.
- Hub schema v5: `dbvc_ac_review_items` gains `installation_epoch`, `event_sequence` (stamped by routing), `drift`, `version_state`, `resolution`, `note`, `classified_at`, `resolved_at`, `resolved_by`, and an `environment_state` key. `ReviewResolutionService::classify()` (explicit, `wp dbvc agency review-classify`) stamps every `observed`/`classified` item with the drift and version state its instance currently has in `FrameworkStatusService` — the report is the only classifier — and resolves automatically when the item's observation is superseded (a newer projection sequence or a new epoch), or the instance reads `clean/current`, or `approved_override/current` with an `approved` (not rebase-flagged) override; everything else stays `classified` until `review-resolve --id --note` records an operator resolution with the actor. Items whose subscription is no longer enabled are left `observed` and counted `unmatched`. `reviews` gains `--state`/`--environment` filters and the drift/version/resolution columns.
- Administrator surfaces (DBVC → Configure → Add-ons → Connected Environments): `Dbvc\AgencyControl\Admin\HubPanel` renders environments (status, epoch, last contact, freshness), an invitation form, open invitations, the framework status report and open review items; `Dbvc\Connected\Admin\InboxPanel` renders the connector's received observations (newest first, acked/pending). - CLI: `compare` now prints `source_exists`/`target_exists` as yes/no/blank.

## What is implemented (M2 step 2: subscriptions, routing, deliveries, inbox, service observer)

### Hub (`addons/agency-control/`, schema v2)

- `dbvc_ac_subscriptions`: client subscriptions (source → target, one row per domain) and framework subscriptions (environment + domain + instance UID → definition UID), typed unique identity, `enabled` flag. `SubscriptionService` validates both ends are enrolled in the same agency/client and refuses self-subscription and unknown domains.
- `RoutingPolicy` (pure, adapted from the package stub; verified against `contracts/examples/registry.json` + `expected-routing.json`): throws on sender-supplied `recipients`/`client_id`/`agency_id`/`audience` and on enrollment/epoch mismatch; client targets require enabled subscription, same agency/client, non-revoked target (held targets still accumulate deliveries); framework review requires an enabled framework subscription and no verified operation receipt (a sender-labelled `apply` origin never suppresses review).
- `RoutingWorker`: consumes `routing_state=pending` events in receipt order, freezes the registry snapshot's revision (`sha256` of the canonical snapshot) on each `dbvc_ac_deliveries` row (`UNIQUE (event_row_id, target)`; `delivery_id` is the target's inbox cursor) and each `dbvc_ac_review_items` row (state `observed` — not "drift" until M3), and marks the event `routed` (or `unroutable` with a reason) in one transaction per event. It runs synchronously right after receipt, so deliveries exist before the ACK returns, and from `wp dbvc agency route`.
- Routes: `GET /inbox?cursor&limit` (≤100) serves only the authenticated target's pending deliveries after the cursor, rechecking at retrieval that the subscription is still enabled and the source not revoked (otherwise the delivery is cancelled with a reason); held/revoked targets get 409/403. `POST /inbox/ack` acknowledges only ids owned by that target (`acked|already_acked|unknown`).
- CLI: `wp dbvc agency subscribe|subscribe-framework|unsubscribe|enable-subscription|subscriptions|route|deliveries|reviews`; `status` adds delivery summaries and review counts.

### Connector (`addons/connected-environments/`, schema v3)

- `dbvc_ce_inbox` (unique on hub `delivery_id` and on source event identity) plus `inbox_cursor`/`inbox_status` on the state row. `InboxWorker` (cron `dbvc_connected_poll_inbox`, self-rescheduling with jitter via `dbvc_connected_inbox_poll_interval`, or `wp dbvc connected poll`): first acknowledges any rows stored but not yet acknowledged (crash recovery), then pages `GET /inbox`, stores each valid item, acknowledges the stored ids, and advances the local cursor only past stored **and** acknowledged deliveries. Received observations are stored for comparison and are never applied to content. Holds mirror the delivery worker's.
- `wp.service` domain: `ServicePostObserver` (profile `wp-service-v1`, post type via `dbvc_connected_service_post_type`, default `service`). Identity is DBVC's `vf_object_uid` (assigned by `DBVC_Sync_Posts::ensure_post_uid_on_save` for DBVC's configured post types — the service type must be in `dbvc_post_types`); a post without it is `identity_missing`, retried, never backfilled. Projection: status, title, slug, content, excerpt, `post_date_gmt`, parent UID, menu order, portable taxonomy terms (`export_tax_input_portable`), and meta through `dbvc_sanitize_post_meta_safe()` + the configured masking rules (`dbvc_mask_apply_to_meta`, `dbvc_mask_apply_to_post_fields`); any masked/removed field marks the projection `complete=false` and leaves only the placeholder in the body. Author, GUID, modified timestamps and numeric IDs are excluded. `PostSignalListener` marks `post:<ID>` on `save_post` (priority 20, after DBVC's UID assignment), `deleted_post` and post-meta hooks; the worker's per-object path emits one settled event per marker and a tombstone after a verified missing/trashed read. Reconciliation (enable, `reconcile`) enumerates the whole type and tombstones posts deleted while disabled.
- Status rows in the Add-ons subtab now show hub connection, last delivery and inbox state; `wp dbvc connected status` includes the same.

## M5 step 2

**Reviewed rollback — done.** `wp dbvc agency rollback --operation` (also `POST dbvc/v1/agency/rollback`) creates an approval-like record (hub schema v9: `approvals.kind` + `rolls_back_operation_id`) bound to a consumed operation's execution digest; it carries no payload. On its next poll the target restores the before image it journalled for that operation, one conditional write per Bricks option container guarded by the operation's *after* fingerprint — a container that moved on since the apply yields a `restore_conflict` and is never overwritten. The restore is verified against the pre-apply fingerprint, journalled as its own `roll-…` operation, and reported; the hub consumes the rollback receipt and regresses the pair baseline to the restored hash (so Compare reads correctly again). Guards: only a `consumed` operation whose outcome wrote (applied/partial/compensated) can be rolled back, only once, and only while the target's epoch is unchanged.

**`wp.service` apply — done.** The connector's Applier now writes service posts as well as Bricks option collections: one conditional per-post write per item, guarded by the post fingerprint (`post_modified_gmt` + raw meta) so an interim editor edit is `stale`, never overwritten. The write sets the post fields, converges managed meta to the received body (keys the body omits are removed; DBVC's own `dbvc_post_history` / `_dbvc_import_hash` bookkeeping is excluded from the projection) and imports the portable terms via `DBVC_Sync_Posts::import_tax_input_for_post`; the result is verified by re-snapshot and compensated back to the journalled before body on a verification miss. Media (attachments) remain unsupported. `ServicePostObserver::capabilities()` now reports `prepare`/`apply` true when the post type is registered and DBVC-configured.

**`wp.service` deletions — done.** A reviewed release deletion (`remove_object`) for a service post executes on the target: the connector **trashes** the post (`ServicePostObserver::trash()` — never a hard delete via sync, so nothing is unrecoverable), the fingerprint guard having passed, journals the before image, and verifies the post left observed coverage (re-snapshot `missing`); a failed verify compensates by untrashing. A reviewed rollback restores it by re-applying the journalled before body (status back to an observed value → the post is untrashed with the same id and portable identity), guarded by the operation's after fingerprint (a post that moved on is a `restore_conflict`, never overwritten). The operation's after fingerprint is recorded from the `delete`/`trashed` journal step. Covered by `ConnectedApplyTest::test_wp_service_deletion_trashes_the_post_and_rollback_restores_it`.

The service storage fingerprint now folds in the projection hash so a same-second content edit still moves it.

## M6 (fleet rollout)

**Step 1 — canary/cohort orchestration (hub) — done.** A *rollout* stages one sealed release across an ordered sequence of *cohorts* of enrolled target environments; cohort 0 is the canary. It is deliberately **not** a distributed transaction — each target is the ordinary single-environment prepare → approve → the-target-executes operation, and nothing here writes to a target directly.

- **Schema (hub v10).** `dbvc_ac_rollouts` (one row per rollout: release, agency/client, `state` running/paused/completed/failed/withdrawn, `current_cohort`, `cohort_count`, `target_count`, `paused_reason`) and `dbvc_ac_rollout_targets` (one row per target: `cohort`, `position`, `state` pending/preparing/approved/succeeded/failed, `operation_id`, `approval_uid`, `outcome`, `detail`), in `Dbvc\AgencyControl\Storage\RolloutStore`.
- **`RolloutService::create($release_uid, $cohorts, $note)`** validates the release is sealed and every target is a distinct, enabled, same-agency/client environment other than the source, then records the plan (targets pending).
- **`RolloutService::advance($rollout_uid)`** is the idempotent driver, safe to call repeatedly (operator, cron or the page). For the current cohort it moves each target one macro-step — request a prepare (reusing `PreparationService`), approve a received ready/no-op receipt (reusing `ApprovalService`), then read the execution outcome the target posted — and applies the **cohort gate**: the next cohort opens (and its prepares are kicked in the same pass) only once *every* current-cohort target reached a verified execution outcome (`applied`/`noop`); a single target failure (`stale`/`failed`/`compensated`/`partial`/`unsupported`/`restore_conflict`, or a prepare/approve error) sets the rollout `paused` so later cohorts never start. The last cohort verifying completes the rollout.
- **Pause / resume / retry / withdraw.** `pause` stops a running rollout; `resume` cannot blow past a failure (the next advance re-pauses while a current-cohort target is still failed); `retry($rollout_uid, $target)` resets one failed target to pending (the rollout stays paused until resumed); `withdraw` closes it (targets already applied are not reverted — that is `rollback`).
- **Surfaces.** `wp dbvc agency rollout-create|rollout-advance|rollout-pause|rollout-resume|rollout-retry|rollout-withdraw|rollouts` and the matching `dbvc/v1/agency/rollout-*` + `agency/rollouts` administrator routes (cookie + nonce + `manage_options`, `no-store`), wrapping the `DBVC_Agency_CLI_Inspector` methods. Capability record: `addon.agency_control.fleet_rollout`.
- **Tests.** `ConnectedRolloutTest` (3 tests, 135 assertions): a canary gates the next cohort and a healthy two-cohort fleet completes (proving an approved-but-unexecuted canary does *not* open the next cohort); a canary failure pauses the later cohort until the target is retried and resumed; and create validates the plan (unsealed/missing release, self, scope, duplicate, unknown target, no cohorts) with a withdraw path. Targets enrolled directly on the hub; their prepare and execution receipts delivered through the same store/service the connector uses.

**Step 2 — the Rollouts page (hub) — done.** The Connected Environments admin page gains a **Rollouts** section (`src/connected-app/index.js`, the `Rollouts` component; built to `build/connected-app.*`). It reads `agency/rollouts` and `agency/releases` and offers:
- **A composer** that builds a rollout from a sealed release: each enabled target (other than the release source) is assigned to a cohort via a per-row select (Excluded / Canary / Cohort 2…); the plan is grouped into the ordered `cohorts` array and posted to `agency/rollout-create`. A live summary shows the cohort/target counts and gates the Create button until at least the canary is assigned.
- **A detail view** with the rollout's state badge, facts (release, source, note, pause reason) and the controls that match its state — **Advance** (idempotent; re-run as targets report), **Pause**/**Resume**, and **Withdraw…** (a binding modal that notes applied targets are not reverted) — over `agency/rollout-advance|rollout-pause|rollout-resume|rollout-withdraw`.
- **Per-cohort, per-target progress**: targets grouped by cohort (the canary labelled, the current cohort marked), each with state and outcome tone badges, a **Retry** on a failed target (`agency/rollout-retry`), and an expandable **rendering evidence** row that fetches the target's execution receipt (`agency/approvals?approval=…`) and surfaces the execution outcome and its receipt warnings — including the Bricks `generated_css_rebuilt` note (ADR-042: rendering evidence stays its own gate).

A sealed release in the Releases section now offers a **Roll out…** shortcut that opens the composer with that release preset. New tone mappings: `running`/`pending`/`preparing` (directional), `succeeded`/`completed` (positive), `paused` (caution). Verified by a clean production build, `wp-scripts lint-js` (hooks + jsx-a11y), the 90-test `connected-environments` PHPUnit group (the routes and shapes the page consumes), and a built-in-browser render of the built bundle's markup and stylesheet in light and dark.

**Step 3 — retention — done.** Finished rollouts are prunable. `RolloutService::prune($days, $dry_run)` (default window `RETENTION_DAYS_DEFAULT = 30`) deletes rollouts in a terminal state (`completed`/`withdrawn`/`failed`) whose `updated_at` is older than `now − days`, together with their `rollout_targets` rows, via `RolloutStore::prune()` (and `prunable_count()` for the dry run). Running and paused rollouts are never touched, and the approvals/preparations audit trail is untouched (only the rollout bookkeeping is removed). Surfaced as `wp dbvc agency rollout-prune [--days] [--dry-run]`, `POST dbvc/v1/agency/rollout-prune`, and a **Prune finished…** dialog on the Rollouts page (days input + a dry-run preview count). Covered by `ConnectedRolloutTest::test_retention_prunes_only_old_finished_rollouts` (aged completed + withdrawn rollouts pruned; a recent withdrawn one and an aged *running* one kept; dry run counts without deleting; target rows removed with the rollout).

## M7 (media / attachment transfer)

**Why now.** The `wp.service` apply/rollback path (M5 step 2) writes a post's fields, meta and terms, but attachments are the one carve-out still stamped through the code ("Media (attachments) are never created here"). Two consequences make this the next slice, not a nice-to-have:

1. In `DependencyLedger::build()` **both `unresolved` and `unsupported` block the item**, and `service_post()` emits every detected `wp.media` reference as `unsupported`. So *any* released service post whose content carries an inline `wp-image-<id>` or a `wp-content/uploads/…` URL can **never** prepare `READY` today — the apply path only works for media-free posts.
2. The featured image (`_thumbnail_id`) was **not detected at all** (it is a bare-integer meta value, matching neither the `wp-image-<id>` nor the upload-URL scan). A post with only a featured image would prepare `READY` and then apply with `_thumbnail_id` set to a **source** attachment id that does not exist on the target — a silently broken/blank featured image.

Media rides as a **sibling channel to the body**, never inside it: a release item `body` is hash-locked to `after_hash` and bounded by `Protocol::MAX_PAYLOAD_BYTES`, so bytes cannot go in the body without breaking the canonicalization contract. Media is modelled as a **dependency of the post that references it** (the existing `wp.media` ledger kind), not a top-level release domain — the operator selects a post, and the media it needs travels with it. **Reuse, not rebuild:** the base plugin already ships the primitives — `DBVC_Media_Sync::format_hash()` (`sha256:` prefix), `find_existing_attachment()`, the `_dbvc_original_attachment_id` / `_dbvc_original_source_url` portable-identity meta, filename preservation, and hash-verified `media_handle_sideload`. The connector reuses these *conventions* in a thin connector-owned path rather than routing releases through DBVC's proposal/bundle machinery (`sync_manifest_media`, `\Dbvc\Media\Resolver`, disk bundles), which is coupled to the local export/backup model and whose dedup helpers are `private`.

**Step 1 — reference detection + portable descriptor + hash identity + ledger local-resolution (target-side; no transport, no apply). — done** (PR #50).
- A connector `MediaReferences` helper enumerates every attachment reference in a decoded canonical body: the featured image `_thumbnail_id` (now detected), inline `wp-image-<id>` in content/meta, and `wp-content/uploads/…` URLs. Each reference keeps its source attachment id (when it has one) and its URL (when it has one).
- `MediaReferences::resolve_local()` answers *does this target already hold the referenced attachment?* — an id reference resolves against a target attachment carrying `_dbvc_original_attachment_id == source_id` (mirroring the base plugin's dedup); a URL reference resolves via `attachment_url_to_postid()` or a `_dbvc_original_source_url` match. Read-only; creates nothing.
- `MediaReferences::descriptor()` builds the **portable descriptor** for a *local* attachment — `{ source_id, hash: 'sha256:<file>', mime, filename, relpath, filesize, url, title, alt, caption }` (via `format_hash()` when the base plugin is present, else a `sha256:` fallback). No bytes yet; this is the contract step 2 fills across the wire.
- `DependencyLedger` consumes it: each `wp.media` entry now carries a real per-reference status — `present` (detail `attachment:<local_id>`) when the target already holds it, else `unresolved` (detail `media_transfer_pending`). Media stops being blanket `unsupported`; a reference the target already has **no longer blocks**, a missing one **still blocks** (honest — never apply a post with dangling image ids/URLs), and the featured image is now among the reported references.
- Fully PHPUnit-tested on one site (`ConnectedMediaTest` + the updated `ConnectedReleaseTest` ledger expectations). No protocol, storage or apply change.

**Step 2 — byte transport. — done** (branch `claude/connected-media-step2`). Media bytes now travel source → hub → target as a sibling channel to the body, never inside it (the body stays hash-locked to `after_hash`).

- **Source** (`ReleaseWorker::serve_payload_requests`). When a `wp.service` item's body is provided, `MediaReferences::collect_for_transport()` resolves each reference to a *local* attachment (`resolve_source()` — on the source the body's ids/URLs are its own), builds the descriptor, and attaches inline base64 bytes, deduped by content hash (a file referenced twice rides once, both refs recorded). It rides on the payload as `media` (and `media_deferred`). Anything unreadable, over `Protocol::MAX_MEDIA_FILE_BYTES` (2 MiB), past the per-item total (`MAX_MEDIA_TOTAL_BYTES`, 4 MiB) or the count cap (`MAX_MEDIA_ITEMS`, 25) is `deferred` (descriptor kept, bytes not) — never silently dropped. A media-bearing payload is posted on its own (`chunk_payloads()`) so one request never carries more than a single item's media.
- **Hub** (`ReleaseService::accept_payloads` → `sanitize_media()`). The hub trusts nothing the source claims: every entry's base64 is decoded, size-capped and **re-hashed against its declared content hash** (a mismatch is `hash_mismatch`, dropped), and the per-item total and count caps are re-enforced. Valid entries + a deferred list are stored on the new `dbvc_ac_release_items.media` LONGTEXT column (hub schema **v11**), beside — and excluded from — the body and the seal digest (the digest still covers only `{domain, instance_uid, profile, operation, after_hash}`). The `payloads` outcome reports `media: {stored, deferred}`.
- **Target** (`PreparationService::pending_for_target`). Each delivered release item now carries `media` (the stored descriptors + bytes) alongside `body`, ready for step 3 to materialize. The prepare receipt is unchanged (media bytes are never echoed back to the hub).

Tests: `ConnectedMediaTest` (source builder — bytes+hash+refs, hash dedup across id/URL refs, `too_large`/`source_missing` deferral) and `ConnectedReleaseTest::test_media_bytes_travel_from_source_to_target_via_the_hub` (a valid + a hash-mismatch + an oversize entry → `{stored:1, deferred:2}`, only the valid one delivered, body/`after_hash` untouched). connected-environments group 102 tests / 2735 assertions.

*Deferred to a later refinement (not step 2):* a fetch-by-hash pull channel for files over the inline cap (so large media is not `deferred`), and offloading stored bytes out of the DB column. Both lift the conservative caps without changing the descriptor contract.

**Step 3 — apply materializes + converges.** *Design decision (2026-09-23, operator-approved):* a media-bearing post must converge under the **hash contract**, not just render. Compare classifies a pair by comparing source vs target vs baseline projection hashes (`Comparison::environment`), and the hub sets the pair baseline to the source's `after_hash` on a verified apply — so if the target's projection hashed its *local* attachment ids/URLs it would read as perpetually `incoming`, never `synchronized`, and rollback/baseline would be meaningless. Therefore attachment references are made **portable (content-hash tokens)** in the wp.service projection. Split into 3a (portable projection + convergence for the already-present/dedup case) and 3b (sideload the carried bytes for the absent case).

**Step 3a — portable media projection + convergence (dedup case). — done** (branch `claude/connected-media-step3`).
- **Token contract.** `MediaReferences::tokenize()` replaces every resolvable local reference — `_thumbnail_id`, an inline `wp-image-<id>` class, and `wp-content/uploads/…` URLs — with a content-hash token `dbvc-media:<sha256hex>`, caching each attachment's hash on it as `_dbvc_media_hash`; an unresolvable reference is left literal (it is content, not managed media). `detokenize()` reverses it, mapping each token back to *this* site's attachment id/URL by content hash (`local_by_hash()`); a token this site cannot resolve is left as-is so the guarded re-snapshot fails rather than storing a broken reference. The round trip is lossless and content-addressed.
- **Projection & apply wiring.** `ServicePostObserver::snapshot()` tokenizes the body before hashing (so the projection hash is site-independent — media-bearing wp.service posts re-hash once, a one-time re-observe/re-baseline; media-free posts unchanged). `ServicePostObserver::apply_body()` detokenizes before the guarded write, so the live post carries real local references while the re-snapshot re-derives the same token and hash. **`Applier::apply_service_item` is unchanged** — the existing `after['semantic_hash'] === after_hash` check now simply passes for a media post whose bytes the target already holds, and compensate/rollback (also `apply_body`) detokenize the same way.
- **Detection, transport, delivery.** `DependencyLedger` resolves each body token: `present` (detail `attachment:<id>`) when this site holds the content by hash — the post converges and does not block — else `unresolved` (`media_transfer_pending`, still blocking). `MediaReferences::collect_for_transport()` and the ledger are now hash/token-based (superseding the step-1 id-mapping). `ApprovalService::pending_for_target` now also delivers `media` on apply-requests (step 2 wired only prepare-requests).
- Tests: `ConnectedMediaTest` — tokenize (resolvable→token, literal left alone, hash cached), lossless round trip, ledger present/blocks, transport by hash, and a **convergence proof** (a post projected on one attachment set, applied onto a fresh target holding the same bytes, re-projects to the *same* `after_hash`). connected-environments group 100 tests / 2720 assertions.

**Step 3b — sideload the carried bytes (absent case). — done** (branch `claude/connected-media-step3b`). Images now land on a target that did not already hold them.
- **Materialize** (`MediaMaterializer`, new): for each carried media entry the target either **reuses** a byte-identical local attachment (matched by content hash — never a duplicate) or **sideloads** a new one from the base64 bytes (`wp_upload_bits` — so WordPress's own upload/type check gates the file — then `wp_insert_attachment` + `wp_generate_attachment_metadata`), stamping the content hash as `_dbvc_media_hash` (plus the base plugin's `_dbvc_original_attachment_id`/`_dbvc_original_source_url`, alt) so `local_by_hash()` and the projection resolve it. The bytes are re-hashed against the declared hash before anything is written; the target trusts nothing it cannot verify.
- **Applier wiring**: `apply_service_item` materializes the item's carried media *before* `apply_body` detokenizes (so every token resolves to a local id/URL), journals the created attachment ids (`step:'media'`, `created_ids` — for step-4 rollback), and **discards** those created attachments if the guarded write is refused or fails verification (a failed apply leaves no orphans). Reused attachments are never touched.
- **Ledger**: a token neither present locally nor carried still blocks; a carried one is `present` (`detail:'carried'`), so a media-bearing post whose bytes the release carries prepares `READY`. `Preparer` passes the prepare-request item's carried media hashes into `DependencyLedger::build`.
- Tests: `ConnectedMediaTest` (materialize sideloads-then-reuses, rejects a hash mismatch, ledger `carried`→present); `ConnectedApplyTest::test_wp_service_apply_sideloads_carried_media_onto_a_target_that_lacks_it` — the end-to-end proof: the source's attachment is deleted, a fresh target lacking it applies the release, the bytes are **sideloaded into a new local attachment**, the post references it, and the post **converges to the source `after_hash`**. connected-environments group 104 tests / 2776 assertions. No hub schema change.

**M7 step 3 is complete** (3a portable projection + convergence, 3b sideload). A media-bearing `wp.service` post now transfers end to end and converges under the hash contract. Step 4 (reviewed rollback deletes only operation-created attachments; Bricks-content/deletion breadth) remains.

**Step 4 — rollback cleanup. — done** (branch `claude/connected-media-step4`). A reviewed rollback now removes the attachments the reversed apply created, closing the media lifecycle.
- `Applier::rollback` reads the reversed operation's journal for its `step:'media'` entries and their `created_ids` (per container). After a wp.service before-image restore **verifies**, it `MediaMaterializer::discard()`s exactly those ids and journals a `step:'media'`/`result:'discarded'` entry. Only attachments that apply *created* (sideloaded) are deleted; a reused or pre-existing attachment is never touched, and nothing is deleted on a failed/`restore_conflict` rollback (the still-applied post keeps its media). Safe because a created attachment's content hash was absent before the apply, so the restored before image cannot reference it.
- Tests: `ConnectedApplyTest::test_reviewed_rollback_deletes_only_the_attachments_the_apply_created` — the after-state references one attachment the target already holds (reused) and one it lacks (sideloaded); after apply both are present, and after rollback the sideloaded one is deleted, the reused one survives, and the post is back at its before image. connected-environments group 105 tests / 2821 assertions.
- *Reviewed deletions:* nothing to add — trashing a service post neither creates nor removes attachments, and rollback of a deletion untrashes the post with its media intact.

*Deferred (M7 addendum, not blocking):* media for **Bricks** content references (a global class/variable could carry an upload URL in its settings) — the tokenize/detokenize/materialize path lives in `ServicePostObserver` and would extend to the Bricks option-collection projection; and the two capacity refinements (a fetch-by-hash pull channel for files over the 2 MiB inline cap, and offloading stored bytes out of the DB column).

**M7 is complete for `wp.service`** — a media-bearing service post transfers end to end (steps 1–3), converges under the hash contract, and rolls back cleanly (step 4). Only the Bricks-content-media extension and the two capacity refinements above remain, each optional.
