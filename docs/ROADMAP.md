## Deferred Configuration Portability Exploration

These are future planning candidates, not approved implementation phases. Draft a dedicated plan only after Configuration Portability Phase 41 closes the single-site workflow, except where an earlier read-only research task is explicitly approved.

| Candidate | Status | Future planning question | Earliest gate |
|---|---|---|---|
| CP-F1 — Writer-capable WP-CLI parity | deferred-planning | Should export, import, apply, and rollback be exposed through WP-CLI, and what confirmation, backup, idempotency, and machine-readable failure contracts are required? | After Phase 41 single-site acceptance |
| CP-F2 — Formal package JSON schemas | deferred-planning | Which package versions and provider payloads need published schemas, compatibility rules, and migration guarantees? | After the P3-P7 package contract is stable |
| CP-F3 — Signed packages | deferred-planning | How should package origin, integrity, key rotation, revocation, expiration, and unsigned-package policy work? | After CP-F2 schema authority; before trusted remote transport |
| CP-F4 — Encrypted secret bundles | deferred-planning | Is secret transport necessary, who owns encryption keys, and how are plaintext exposure, rotation, recovery, and audit handled? | Separate security review after CP-F3; secrets remain excluded by default |
| CP-F5 — Remote baseline registry and site-to-site transport | deferred-planning | What authentication, authorization, signing, replay protection, approval, and rollback contracts are required for remote package pull or push? | After CP-F3 and single-site acceptance |
| CP-F6 — Multisite and fleet propagation | deferred-planning | How are sites selected, staged, rate-limited, observed, stopped, retried, and rolled back without turning one failure into fleet-wide drift? | After CP-F5 proves bounded single-destination transport |
| CP-F7 — Scheduled configuration drift monitoring | deferred-planning | What is the baseline authority, comparison cadence, retention, notification, and false-positive policy, while keeping detection read-only and prohibiting automatic apply? | After package/schema stability; detection-first plan only |
| CP-F8 — Saved review policies and Bricks onboarding integration | deferred-planning | Which reviewed non-secret decisions can be reused safely, and how should Bricks mothership/client onboarding consume them without coupling unrelated sessions? | After Phase 40 environment-policy acceptance |

Cross-cutting rule: none of CP-F1 through CP-F8 authorizes current-value disclosure, secret transport, remote access, automatic apply, fleet mutation, new credentials, or background schedules. Each candidate requires its own threat model, storage contract, failure/rollback design, evidence plan, and explicit approval before implementation.
