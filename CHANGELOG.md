# CHANGELOG

## Unreleased

## 2.2.0 — 2026-10-30
- Security: WS Form form exports and stored backups now follow the `options.json` redaction contract, closing the last S1 gaps. Form files in `third-party/ws-form/forms/` and Entity Editor WS Form snapshots redact form-level meta and every action's settings to `[dbvc-redacted]`: credentials, webhook endpoints and HTTP header values always, recipient fields only when they hold a literal email address (WS Form variables such as `#blog_admin_email` stay). WS Form stores each action's settings as a JSON string, so this uses its own key list (`DBVC_WSForm_Secret_Redactor`), adjustable with `dbvc_is_secret_option_key`; the file checksum is recomputed so WS Form's own import still accepts it. On import a placeholder takes the uid-matched local form's value (actions matched by row ID and type), is dropped for a clone with no match, and an import is refused (`dbvc_wsform_redacted_unresolved`) when the matched form cannot be read; uid matching and ID preservation are unchanged. New backups now harden every subfolder and re-redact `options.json`, `options/*.json` and WS Form form files before the manifest is written, and upload sync and backup restore re-redact WS Form form files too. Backups taken before redaction can be fixed with `wp dbvc redact-backups --user=<admin>`, which previews per-backup folder and file names and counts (never values), asks before writing, and exits after the preview with `--dry-run`; it requires `manage_options`.
- Security: the sync folder can now live outside the web root. Define `DBVC_SYNC_PATH_ABSOLUTE` in `wp-config.php` with an absolute path to a dedicated folder (on Cloudways, `private_html/dbvc-sync` beside `public_html`). Every sync-folder reader and writer then uses it in place of the ABSPATH-relative `dbvc_sync_path` option. This is the structural fix for the S1 exposure: nginx ignores the folder's `.htaccess`, so redaction alone still left plugin lists, user roles and settings downloadable. The value is validated (`DBVC_Sync_Location`). DBVC refuses relative paths, `.`/`..` segments, unsafe characters, the filesystem root, top-level folders, system folders, any folder inside ABSPATH, wp-content, plugins, themes or uploads (after resolving symlinks), and any folder that contains the install. A refused value falls back to the previous location and shows a critical Site Health result and an admin notice on DBVC screens. The location can only be set in code (the constant, or the `dbvc_sync_path_absolute` filter); the admin field turns read-only while it is active, and configuration portability cannot carry a server path between sites. `dbvc_is_safe_file_path()`, `DBVC_Sync_Posts::is_safe_file_path()` and the clear-sync-folder guards accept the absolute root, and now compare on path-segment boundaries, so a sibling such as `sync-evil/` no longer passes a prefix test. Clearing the sync folder never removes the configured absolute root itself. A new Site Health test (`dbvc_sync_folder_location`) reports a web-reachable sync folder from a filesystem check, without making any HTTP request. Backups, proposals, transfer packets and media bundles still live under `uploads/sync/`.
- Security: the other sync-folder writers now follow the `options.json` redaction contract, since the folder sits under ABSPATH and nginx ignores its `.htaccess`. ACF options-group files (`options/{group}.json`, written after every options export) redact ACF password fields and secret-named fields and sub-fields to `[dbvc-redacted]`, and options-group import keeps the target's own value wherever it finds the placeholder. Entity Editor pre-replace snapshots apply the configured meta masking and then the secret-name redaction to post and term meta, and their folder (`.dbvc_entity_editor_backups/`) now gets the `.htaccess`/`index.php` deny files. Snapshot and `.bak.json` names carry a random suffix, so their URLs can no longer be guessed from the entity path and timestamp. Upload sync and backup restore now harden every folder they write and redact `options.json` and `options/*.json` again, so a restored pre-redaction export no longer re-exposes secrets. Opt out of the re-redaction with `dbvc_redact_restored_option_exports`. A new `dbvc_export_options_on_update` setting (default on, unchanged behaviour) lets a site stop rewriting `options.json` on every option save.
- Security: `options.json` no longer carries secret-shaped option values. The generic options export runs on every admin option save, plugin (de)activation, theme switch, customizer/widget/term/comment/profile change, the admin export and `wp dbvc export`, and writes under ABSPATH where the `.htaccess` deny does nothing on nginx — on LocalWP the file was served with HTTP 200 and every licence key and API secret in clear. Licence keys, API keys and tokens, passwords, salts and credentials — as whole options (`bricks_license_key`, `dbvc_bricks_api_secret`) or nested inside settings arrays (`imagify_settings.api_key`, `smtp.pass`) — are now written as `[dbvc-redacted]`. On import the placeholder means "keep this site's own value": a redacted whole option is skipped, and a redacted nested field takes the target's value at the same path or is dropped, so a redacted export never overwrites the target's secrets with the placeholder. Classification is a name heuristic (`DBVC_Options_Secret_Redactor`); adjust it with the `dbvc_is_secret_option_key` filter. Non-secret option values are still exported and still web-readable unless the server blocks the sync path. Existing `options.json` files keep their secrets until the next export rewrites them.
- WS Form references in post meta are now portable. A post whose meta points at a WS Form form by raw ID (the Vertical framework's `custom_wsform` and `core_allpostypes_controls_objects_custom_wsform`) exports an additive `dbvc_wsform_refs` sidecar carrying each form's portable uid, and import resolves that uid to the matching local form. The raw ID is deliberately never replaced in the payload — the consumer is ACF at render time, so a token that reached a site which could not detokenize it would be worse than a wrong ID; an unresolvable reference survives exactly as exported and is reported in `dbvc_post_history`. Opt out with `dbvc_wsform_reference_remap`; extend coverage with `dbvc_wsform_reference_meta_keys`. Only an unambiguous positive integer is ever rewritten, and ACF's `_`-prefixed companion keys can never be candidates.
- Import ordering: third-party entities are now imported **before** the post loop in both `import_all()` and the WP-CLI batched import. Previously they ran last, so a first-ever import of a sync folder left every post that referenced a form unresolved until a second full import run.
- Opt-in WS Form object-ID preservation (`dbvc_third_party_portability_wsform_preserve_ids`, default off, plus a `dbvc_third_party_wsform_preserve_ids` filter and an admin checkbox). Renumbering stays the default because it is correct when cloning a form to a new identity; preservation is correct when updating a uid-matched form, since submission meta keys are `field_<id>` and `#field(id)` references are stored by ID. A pre-flight guard refuses the import when any incoming group/section/field ID belongs to a different form on this site — WS Form's child tables share one global `AUTO_INCREMENT` space and its upsert probes only whether an ID exists, never whether this form owns it — and the write runs in a transaction when the tables are InnoDB, degrading to guard-only rather than claiming a rollback it cannot deliver.
- WS Form exports now report forms they could not write instead of dropping them. The include-trash setting was a silent no-op: WS Form's `db_read()` throws for a trashed form, so DBVC skipped it and the returned file count could not express the loss. Skips are classified (`trash_unreadable`, `unreadable`, `unsafe_path`, `encode_failed`, `write_failed`), named in the admin notice with an actionable message, logged, and readable via `get_last_wsform_export_report()`, with `forms_considered == forms_written + forms_skipped`.
- Fixed: the WS Form uid accessor minted and persisted a uid row for a form ID absent locally, because the auto-export on post status transition runs before an import remaps a reference. That left an orphan `wsf_form_meta` row and claimed the uid against an ID a later form could occupy, which would then resolve as a false identity match.
- `wp.service` deletions (reviewed): an approved release deletion (`remove_object`) for a service post now executes on the target — the connector **trashes** the post (never a hard delete via sync), guarded by the post fingerprint and journalled, verified by the post leaving observed coverage, and compensated (untrashed) on a failed verify. A reviewed rollback restores it (untrashed, same post id and portable identity), guarded by the operation's after fingerprint. Media/attachment transfer is still unsupported.
- `wp.service` apply with masked fields: a service post whose projection is incomplete only because a field is masked (e.g. `post_date_gmt` in the export-mask config) no longer blocks preparation — it prepares and applies over its unmasked fields. Masking is treated as a deliberate, out-of-the-sync-contract exclusion: the prepare proceeds on masking-only incompleteness (the managed-set hash is authoritative), and apply never writes or deletes a masked post field or masked meta key (it preserves the target's value), mirroring the projection. Real incompleteness (canonicalization failure, missing identity) still blocks.
- Connected Environments page — colour readability (light + dark): fixed low-contrast text on the admin page. The active section-nav tab no longer renders white-on-near-white in dark mode (it inverts with the surface token); `--dbvc-ce-color-text-subtle` is darkened in light mode (`#6b7280`) and lightened in dark (`#a7aaad`) so the "…· as of …" line and small timestamps clear WCAG AA; link text gets a lifted accent token in dark so it reads on tinted panels; and in dark mode the app now paints its own dark canvas so the header, nav and as-of text stay readable even when WordPress admin itself is light. Verified in both `prefers-color-scheme` values; details in `docs/implementation/active/connected-environments-admin-page.md` §5.4.
- Fleet-rollout retention (M6 step 3): finished rollouts can be pruned. `wp dbvc agency rollout-prune [--days=30] [--dry-run]` (and `POST dbvc/v1/agency/rollout-prune`) deletes rollouts in a terminal state (completed, withdrawn or failed) whose last change is older than the window, together with their target rows; running and paused rollouts are never removed and applied targets are unaffected. The Rollouts admin page gains a "Prune finished…" dialog with a days input and a dry-run preview of how many would be removed.
- Connected Environments page — Rollouts (M6 step 2): a hub Rollouts section drives fleet rollouts from the admin page. A composer builds a rollout from a sealed release by assigning enabled targets to ordered cohorts (canary first); the detail view shows per-cohort, per-target progress with tone badges, Advance / Pause / Resume / Withdraw controls, a Retry on a failed target, and expandable per-target rendering evidence (the execution outcome and receipt warnings, including the Bricks `generated_css_rebuilt` note). A sealed release in Releases now offers a "Roll out…" shortcut. No new backend — it wraps the M6 step 1 `agency/rollout-*` and `agency/rollouts` routes.
- Fleet rollout (M6 step 1): the hub can stage a sealed release across an ordered sequence of cohorts of target environments — the canary first — with `wp dbvc agency rollout-create --release --cohorts=<canary;a,b;c>` (and `POST dbvc/v1/agency/rollout-create`). `rollout-advance` drives each target of the current cohort through the ordinary single-environment prepare → approve → execute path and opens the next cohort only once every target in the current one has verified; a single target failure pauses the rollout so later cohorts never start (`rollout-pause|rollout-resume|rollout-retry|rollout-withdraw|rollouts`, matching admin routes). It is not a distributed transaction — each target is one independent operation — and no target is written directly. Hub schema v10 adds `dbvc_ac_rollouts` and `dbvc_ac_rollout_targets`.
- Bricks CSS regeneration (M5 step 2): after an apply or rollback that writes Bricks option collections, the connector regenerates Bricks' cached CSS files via `\Bricks\Assets_Files::regenerate_css_files()` when Bricks uses external-file CSS mode (a no-op in inline mode); the execution receipt reports `generated_css_rebuilt`.
- `wp.service` rollback (M5 step 2): a reviewed rollback now restores service posts too — the reversed operation's pre-apply post body is re-applied, guarded by its after fingerprint (a post changed since the apply is a restore conflict, never overwritten) and verified. The service storage fingerprint now includes the projection hash so a same-second content edit still moves it.
- Connected Environments page: the Releases Execute step now offers a Roll back… action (with a binding confirm dialog) on an applied operation, posting `dbvc/v1/agency/rollback` — the administrator rollback action beside the CLI.
- `wp.service` apply (M5 step 2): approved releases now write service posts on the target as well as Bricks option collections — one conditional per-post write guarded by the post fingerprint (post_modified + meta), converging post fields, managed meta and portable terms, verified by re-snapshot and compensated on a miss. Media and service deletions stay unsupported. DBVC's own history/import-hash meta is excluded from the wp.service projection.
- Reviewed rollback (M5 step 2): `wp dbvc agency rollback --operation` (and `POST dbvc/v1/agency/rollback`) reverses a consumed release operation — the target restores the before image it journalled, one conditional write per Bricks option container guarded by the operation's after fingerprint (a container that changed since the apply is a restore conflict, never an overwrite), verified and reported, and the hub regresses the pair baseline to the restored hash. Hub schema v9 adds `approvals.kind` and `rolls_back_operation_id`.

- Connected Environments page, slice A6: a connector-role Activity section — the site's own outbox (with delivery-state and domain filters and a Reconcile runner), the inbox of received observations grouped by source (never applied), and the release receipts + execution journal it produced, with an apply-gate banner.
- Connected Environments page, slice A5: a release composer on Compare's outgoing rows (select objects → create a release) and a hub Releases section with a manifest → prepare → approve → execute stepper — prepare-receipt detail (identity, container fingerprint, patch, dependency ledger, blockers, hub notes), a binding approval dialog, and the read-only execution receipt.
- Connected Environments page, slice A4: hub Framework section — Status (framework-status report with drift/version badges, Adopt desired, Approve override with rationale, Detach override, subscribe-an-object form), Definitions (grouped versions, Set desired, publish form from hash / environment object / copied version) and Reviews (state chips, Classify now, Resolve with note).
- Connected Environments page, slice A3: hub Compare section (same-client pair picker, domain filter, freshness/coverage banner, state chips as filters, hash-prefix rows with Confirm baseline / Accept absent / Link instance… actions) and an object drawer (identity, both sides' projections, baselines, recent events); `wp dbvc agency events|projections|baselines` accept `--instance=<uid>`.
- Connected Environments page, slice A2: hub Environments section (registry table with freshness, Hold with an operator note, Release hold, Revoke with inline confirmation), invitation form whose token is shown once in a modal with the enroll command, and an invitations list; new `wp dbvc agency hold --environment [--reason]` and `wp dbvc agency invitations [--open]` plus the matching `agency/hold` and `agency/invitations` admin routes.
- Added a dedicated `DBVC Export → Connected Environments` admin page (slice A1), present only while the connector or hub gate is ready: role-adaptive overview (hub stat cards and attention list; connector connection, coverage and pending-work cards with runner buttons), a Settings section (gates, apply-gate confirmation, enrollment and resume) and a "Run now" menu, backed by cookie + nonce `manage_options` admin REST routes under `dbvc/v1` (`connected-admin/{overview,settings}`, `connected/*`, `agency/*`) that wrap the WP-CLI inspectors and answer `no-store`.

- The connector can enroll with a hub (`wp dbvc connected enroll`), stores the credential sealed with the installation salts, delivers outbox batches outbound-only with per-event settlement (`wp dbvc connected deliver|resume`), and polls its hub inbox storing deliveries before acknowledging (`wp dbvc connected poll|inbox`); received observations are never applied.

- One guarded round trip (M5 step 1): the hub can approve a ready prepare receipt (`wp dbvc agency approve|revoke-approval|approvals`), and a connector whose new apply gate is on (`dbvc_addon_connected_environments_apply_enabled`, off by default) executes it on its next poll: Bricks global classes/variables only, one conditional SQL write per option container guarded by the receipt's storage fingerprint, journalled before image (`wp dbvc connected operations`), after-state verified through the read-only observer, compensation on failed verification, `stale` instead of overwrite when the container changed, the change reported with `origin=apply`, and the pair baseline advanced for verified objects.
